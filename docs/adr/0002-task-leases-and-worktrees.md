# 0002: Аренды задач, worktree на задачу и именованные ресурсы вместо общего repository-wide lease

Status: accepted (владелец одобрил миграцию 2026-11-08, issue #18)

## Context

До #18 вся работа шла под одним lease координатора (`autonomy/coordination.py`, состояние `state.active` в `<git-common-dir>/autonomy-coordination/`). Любая запись в план, очередь или код требовала этого lease, поэтому независимые задачи выстраивались в очередь даже в отдельных worktree (они делят Git common dir), ревью и ожидание CI держали тот же mutex, а мёртвый или неактивный координатор блокировал весь репозиторий. Сочетание «один lease на всё» и «закончи работников до ответа» не оставляло санкционированного пути для фоновой работы, и в соседнем проекте это привело к передаче lease делегату — «фоновому координатору» — и к цепочке делегатов второго уровня через CLI. Анализ и переносимый набор: `/home/happier/autonomy` (`README.md`, `docs/WORKFLOW.md`, `docs/DELEGATION.md`, `docs/REVIEW.md`).

## Decision

- В репозиторий скопирован `autonomy/autonomyctl.py` (stdlib-only) с тестами. Состояние — `<git-common-dir>/autonomy-coordination-v2/`, не коммитится. `flock` держится только на одну атомарную транзакцию. Локальная адаптация: `workspace-create` по умолчанию от `origin/master`.
- Аренда задачи (`claim --task issue-N`) исключает только повторное выполнение этой задачи; аренды разных задач сосуществуют. Каждая пишущая задача получает свою ветку и worktree. Метка `status:in-progress` ставится после успешного claim; метки остаются долговременным отображаемым состоянием, а не атомарным захватом.
- Именованные аренды ресурсов сериализуют только реально общие ресурсы: `integration:master`, `screeps-server:live`, `screeps-world:<room>`, `ports:<range>`. Интеграция в `master` — короткий сериализованный шаг под `integration:master` из worktree задачи (`git fetch`, rebase на `origin/master`, повторный прогон затронутых проверок, `git push origin HEAD:master`; основной checkout — только fast-forward и только если он чист) или PR.
- Истечение аренды не разрешает takeover; восстановление — `recover --confirm-stopped` после проверки, что прежний владелец и его runs остановлены; другие задачи этого не ждут.
- Глубина делегирования — одна на любом маршруте. Делегат — лист, правило вставляется в общий хвост каждого поручения; аренда делегату не передаётся; фоновая работа — отдельная top-level сессия задачи. Маршрут по умолчанию — нативные субагенты (предпочтительно `gpt-6.1-terra`), Happier-managed — только по явной просьбе; это сознательно отменяет правило 3 набора (запуск только через Happier MCP).
- `coordination.py` и его тесты удалены. Финализация расписания из `coordination.py release` перенесена в `automation_pause.py --finalize`: пауза только при пустой очереди GitHub (нет ready/in-progress/review) и отсутствии в реестре v2 чужих claims (кроме собственного живого claim без runs), с долговременной квитанцией против повторного POST; ошибка сообщается и не мешает `finish`. Остальные свойства (конфиг вне checkout, выключено по умолчанию, только локальный URL, без редиректов, readback, без вывода секретов, тесты только на подделках) сохранены.

## Alternatives

- Оставить общий lease и добавить worktree — не даёт параллельности: lease глобален для всех linked worktree.
- Захват через метки GitHub — не атомарен: две сессии могут одновременно прочитать `status:ready`.
- Распределённый реестр (база с compare-and-swap) — избыточен для одной машины; при работе с нескольких хостов понадобится трекер/PR или такой сервис.
- Подключить набор как внешнюю зависимость вместо копии — владелец выбрал копию, чтобы репозиторий был самодостаточен.

## Consequences

- Независимые задачи идут параллельно; конфликты переходят на этап интеграции, где их разрешает интегратор под `integration:master`.
- Пути в задаче — подсказки для планирования, а не блокировки.
- `flock` координирует только сессии на этой машине.
- Старое состояние `<git-common-dir>/autonomy-coordination/` сохраняется как история и больше не читается; lease миграции освобождает координатор сохранённой копией старого скрипта.
- Окна гонки при паузе расписания: очередь GitHub читается вне блокировки, а проверка реестра не удерживается во время HTTP, поэтому issue, ставший готовым, или сессия, взявшая задачу сразу после проверок, не учитываются. Такая работа не останавливается — пауза лишь прекращает следующие плановые запуски до возобновления владельцем.
- Частично заменяет [ADR 0001](0001-github-issues-task-workflow.md): «общий lease» и «одна рабочая ветка» больше не действуют; очередь GitHub Issues, запрет fallback и fail-closed остаются в силе.
