# Tick gate research (admission BLOCKED)

The files `e2e/server/step-mod.js`, `step-client.js` and `snapshot-client.js` are a **research prototype**, not a per-tick snapshot API. An acknowledgement with status `cycle-finished-unverified` means the main loop emitted the expected stages in order, the recorded writer journals show the queued user/room work saved without journal-recorded errors, the instrumented detached writers were drained into the queue/custom-stage barriers, and no field-set storage write was journaled after the drain started. It does not by itself certify a coherent DB/Memory snapshot: snapshot coherence additionally requires the controller-side checks (`captureSnapshot` in `e2e/server/snapshot-client.js`) — calibrated `gameTime` binding, double-read stability, a post-barrier journal cross-check, field-key expiry checks and complete instrumentation coverage. The drain/snapshot machinery has now been executed on disposable instances (run IDs in the drain-extension section below: three coherent bound snapshots, negative controls detected via journal+ack, all nine fault cases at expected verdicts) — that is narrow single-world evidence, still not proof of general snapshot safety. **Do not use it to admit HAR or scenario tests.**

The mod requires a factory-created isolated root, its `ownership.json`, and matching `SCREEPS_E2E_ROOT` and `SCREEPS_E2E_MARKER` in the child environment. Identity failure exits the process because the upstream mod loader catches exceptions. The factory supplies `step-preload.js` explicitly. It checks the isolated marker and the pinned installed engine-main hash, then changes exactly two scheduler call sites in memory: initial `loop()` becomes `global.__screepsStepSchedule(loop, 0)`, and `setTimeout(loop, delay)` becomes `global.__screepsStepSchedule(loop, delay)`. Transformed SHA-256 is `35a1441758844b9f9fbad0de0502043d72153a97e4d833d534ca592e7b971212`. No installed files are changed. Hash or exact-match drift fails startup. The main process creates `step-control` exclusively; a stale directory makes a restart fail closed. A session-specific, sequential command file allows entry into one complete main loop. At `finish` an ack records the complete observed stage sequence; missing stages are UNKNOWN. The next loop remains gated. Client timeout, malformed ack, or a second concurrent operation invalidates the controller; after a timeout the caller must quarantine the instance and never retry the command. The mechanism has not been proven safe against competing controllers or external writers. It must not be loaded on a shared server.

## Source findings

Read-only inspection of installed packages under `~/screeps/node_modules/@screeps` on Node v22.23.4: engine 4.3.0, driver 5.3.0, launcher 4.2.0, storage 5.1.3. Launcher resolves engine `dist/main.js`, `dist/runner.js` and `dist/processor.js`; the corresponding readable `src` files show the same relevant control flow. SHA-256 of executed files:

- engine/dist/runner.js: `098e39a5bdf65128888829a0fc3ce3199efa943b237925b68685c131241078a8`
- engine/dist/processor.js: `53ae81ea0455b64359087dbdb638452acbaf62e61af3ad5e1023f1300e901341`
- driver/lib/index.js: `2080ac77155c822451534ffd1794a2732de9f999bcf0074853e38aea12a15e44`

Main emits `start`, calls `notifyTickStarted`, queues active users and waits, queues active rooms and waits, runs `commitDbBulk`, global processor, a second `commitDbBulk`, increments game time, publishes rooms done, runs custom stage, and emits `finish`. Both `commitDbBulk` calls in this driver return an already-resolved promise. The original notifyTickStarted gate entered the main loop before waiting; its reset interval invoked `queue.resetAll()` repeatedly during a stalled repeat. The current preload places the gate before main-loop entry, so the reset timer has not started while waiting. Its causal role in the old CLI timeout is unknown; long holds beyond the measured two 6.5-second cases remain untested. `pauseSimulation` sets an environment flag checked by `notifyTickStarted`; neither that response nor `roomsDone` alone waits for all relevant writers.

The runner catches runtime rejection as a result and still marks its user queue item done. Its Memory, segment and intent saves are awaited, but console/error notification work is not necessarily awaited. The research mod disables backend cron jobs in this isolated topology before the backend starts its interval and the long-hold probe checks for a backend marker and absence of cron execution; this changes the supported environment and does not establish that all other writers are excluded. The processor catches `processRoom` errors, then clears intents and marks the room queue item done; thus queue completion or stage order alone is not proof of effects. Room object and event-log bulk writes are included in the process promise, but `activateRoom`, history persistence and room-stat saves are invoked without awaiting them. The test mod wraps the real processor `activateRoom` promise and drains it before room queue `markDone`; on an isolated run, injecting a 1200 ms activation delay delayed each of three acknowledgements, and a rejected activation produced an UNKNOWN timeout and quarantined instance. A 6500 ms activation delay triggered the engine reset interval and yielded UNKNOWN; the hook records reset occurrence and rejects the cycle. This is narrow evidence for that one writer; The processor journal records room stages and caught processing errors, and acknowledgement checks journal deltas against queued users and rooms. The processor `finish` event may occur before asynchronous room work completes and is not a completion signal. Completeness of failure detection and other detached writers remain unproven. The history channel therefore cannot be treated as part of an atomic snapshot at `finish`. Main's accessible-room and room-status updates are also launched without awaiting them. Other background writers and active API clients have not been fenced.

## Drain extension and bound snapshot — implemented, executed 2026-11 (run IDs below)

The mod now additionally:

- **Storage-write journal (RPC choke point).** Mods load inside `common.configManager.load()` strictly before `common.storage._connect()` in every process (backend/lib/index.js:14→16, driver/lib/index.js:95→101), so `storage.env`/`storage.db` are still empty facades at mod-load time and cannot be wrapped directly (the previous design stamped markers on the pre-connect facades and ended up with zero wrapped methods). The mod instead wraps `RpcClient.prototype.request` (common/lib/rpc.js:125) — the single point every env/db/queue/pubsub op flows through once `_connect()` binds the client. Mutations append `{kind:'store', seq, proc, op, key|collection, fs, aux, t}` records plus `store-done`/`store-error` terminals (matched by per-process `seq`) to `step-journal-<pid>.jsonl`. Pure reads (`dbEnvGet`, `db.find`, `dbFindEx`, …) are not journaled. `fs` marks the chosen field set: env keys `gameTime`, `activeRooms`, `memory:*` and db collection `rooms.objects`; `accessibleRooms`/`roomStatusData` are `aux` runtime inputs. **`db.clear` is a mutation, not a read** — it deletes every document in a collection.
- **Auto-drain.** Every journaled *mutation* promise is registered into a per-process pending set: processor ops drain before `rooms` queue `markDone`, runner ops drain before `users` queue `markDone`, main ops drain inside the custom stage before the barrier timestamp. Long-poll waits (`queueFetch`, `queueWhenAllDone`) are journaled but **never** drain-tracked — an in-flight fetch parked in the drain set deadlocks `markDone` because processor.js issues the next `fetch` without awaiting the previous room's detached `processRoom→markDone` chain (observed live: a parked fetch held one room's markDone ~4.8s until the watchdog reset). **Rejected promises stay in the drain set** — a fault that settles before the drain snapshot must still be seen; removal-on-reject silently skipped rejected writers and produced verified acks (fail-open, now fixed).
- **Named detached-writer hooks (whitelist, never regex).** Processor: `activateRoom` (`activate-fault.json`), `driver.history.saveTick`/`upload` (`history-fault.json`), `roomsStatsSave` (`roomstat-fault.json`). Runner: `sendConsoleMessages`, `sendConsoleError`, `sendNotification` (`notify-fault.json`), plus the awaited `saveUserMemory` (`memory-fault.json`). Main: `activateRoom` (drain-only), `updateAccessibleRoomsList`/`updateRoomStatusData` (`access-rooms-fault.json`, `room-status-fault.json`). Regex sweeps are forbidden: the old `/roomstat|stat.*room/i` sweep promisified the sync factory `getRoomStatsUpdater` and broke every room with `stats.inc is not a function`. `driver.sendNotification` fired from processor intent ticks is not a named hook but its storage writes are auto-drained by the rpc tracker.
- **Forced gated-writer invocation.** `updateAccessibleRoomsList`/`updateRoomStatusData` only run spontaneously when `gameTime > lastUpdate + 20` (engine/dist/main.js:79). A present `access-rooms-fault.json`/`room-status-fault.json` makes the mod invoke the same (wrapped, journaled, drained) writer at the `incrementGameTime` stage — this is how fault probes exercise the gated writers below tick 21 and how the hold-probe 6500 ms calibration engages the watchdog.
- **Coverage files.** `step-coverage-<role>-<pid>.json` records installed hooks and `storage.{mode:'rpc', rpcWrapped, envWrapped, dbWrapped, resolved, connected}`. The ack embeds a `coverage` scan; `captureSnapshot` independently refuses to certify when coverage is degraded.
- **Barrier and ack fields.** Inside the custom stage the mod records `drainStartTs`, drains `globalPending`, records `barrierTs`, and at `finish` scans all journals. A field-set write is a violation iff it was initiated after `barrierTs` **or** lacks a terminal (store-done/error) at or before `barrierTs` — a delayed-but-drained writer is *not* flagged; an untracked straggler or post-barrier write is. `drains` are scoped to the cycle (`t >= cycleStartTs`). The ack carries `gameTime` (bound by wrapping `driver.incrementGameTime`, whose resolution is the new time since `env.set` resolves to the written value; `getGameTime` fallback), `gameTimeBound`, `engineSurface`, `drains`, `postBarrierWrites`, `coverage`, `status`.
- **Fail-closed validity.** `status: 'cycle-finished-unverified'` additionally requires `journalArmed` (rpc wrap live) and, when the pinned driver surface is present (`engineSurface`: `incrementGameTime`/`getGameTime`/`getRoomStatsUpdater`/`makeRuntime` all functions — always true under the manifest-pinned driver, false only for the synthetic offline harness in step-selftest), a finite `gameTime` and `coverage.complete` across main/runner/processor. Arming itself fails closed (`exit 78`) rather than degrading.
- **Bound snapshot.** `captureSnapshot` requires: a verified ack with finite `gameTime`, `drainStartTs`/`barrierTs`, zero `postBarrierWrites`, complete coverage, a double read of the field set `settleMs` apart that is byte-identical and equal to `ack.gameTime`, zero violating field-set journal writes (same terminal-matching semantics as the ack scan), and `ttl == -1` on the field-set env keys. User/room queue emptiness is asserted via the stage sequence plus drain bookkeeping; it is not directly readable through the CLI and remains a documented limitation.
- **Negative-control hook.** `step-control/injected-write.json` consumed inside the custom stage performs one deliberately untracked journaled field-set write after the barrier (through the real storage facade → rpc journal). It must flip the ack to `unknown` or lose it; the probe fails loudly if a verified ack survives.

**Non-atomic activeRooms read.** `driver.getActiveRooms` does `smembers` then `del` as two ops. Under the gate the pair is fenced by construction: all `activateRoom` writers (processor and main) are drained before the barrier, backend `roomsForceUpdate` is disabled, and no other client is permitted, so no foreign `sadd` can interleave. A foreign `sadd` would also appear in the journal as an unattributed field-set write. In `SCREEPS_E2E_KEEP_CRON=1` mode or with any additional client the pair remains racy — that mode stays out of the snapshot contract.

**Runner console/error notification work** (`runner.js:~23-28`, not awaited) is drained at user `markDone` via the whitelisted `sendConsoleMessages`/`sendConsoleError`/`sendNotification` hooks plus the rpc-tracked auto-drain for any storage write they issue. Transient pubsub console output is not durable state and is classified out-of-contract; error notifications land in `users.notifications`, are journaled, and are outside the chosen field set.

**Processor loop concurrency (newly measured).** `processor.js` does not return the `processRoom→clearRoomIntents→markDone` chain from its outer `.then` — the next `fetch` is issued while the previous room's chain is still detached. MarkDone drains therefore can (and do) observe the *next* room's in-flight writes; the drain covers them conservatively. `runner_threads` must stay `1` (as pinned in the factory `.screepsrc`): with `startLoop` pool size >1 the same fetch-overlap could deadlock the users-queue drain on a parked `queueFetch`.

**Known limits.** (1) `updateAccessibleRoomsList`/`updateRoomStatusData` run spontaneously only at `gameTime > lastUpdate + 20` (engine/dist/main.js:79); fault coverage below tick 21 comes from the forced-writer path only, and spontaneous-writer drift at tick ≥21 is separately unprobed. (2) Any injected `delayMs` above `mainLoopResetInterval` (5000) produces UNKNOWN via the watchdog `queue.resetAll`, not a stretched ack — sub-5s delays are the observable signal. (3) Storage-process-internal writers (env expiry deleter, autosave) are not journaled; field-set keys are asserted `ttl == -1` and autosave is a disk artifact, not logical state. (4) `driver.queue.create` must be called after the mod's `init` hook for queue-drain wrapping to bind. (5) A storage mutation that rejects stays in the drain set and wedges subsequent drains — deliberate fail-closed behavior; a rejecting op in a healthy run is an anomaly and yields UNKNOWN.

The drain/journal implementation above is an attempt at that accounting: failures and delayed writers are now routed into queue/custom-stage barriers, the command is bound to the calibrated Game.time reported in the ack, and the chosen field set is checked quiescent via barrier, double-read and journal cross-check. Until the snapshot probes run, every clause of that sentence remains unproven for this mechanism. Logs, notifications, history and intents still require separately identified provenance and timing; their availability and consistency are currently unknown. A stable gameTime surrounding reads does not supply this proof, which is why the snapshot additionally requires barrier evidence, journal cross-check and coverage.

No comparable observer-disabled baseline or CPU measurement has been collected, so CPU overhead and normal-load overhead remain unknown. The new journal adds a synchronous file append to every journaled storage write; its cost is unmeasured. Injected delays are fault tests, not overhead measurements.
