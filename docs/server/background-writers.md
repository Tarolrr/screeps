# Фоновые записи при исследовании fence

Статус: анализ исходников установленной версии, не экспериментальное доказательство quiescence. Исследованы backend 3.3.0, driver 5.3.0, storage 5.1.3 и engine 4.3.0 из `~/screeps/node_modules/@screeps`; живой сервер и файлы установки не менялись. Ниже «обязательные поля» означает выбранные `rooms.objects`, `memory:<userId>`, `gameTime`, `activeRooms` и очереди пользователей/комнат; history, логи и CPU требуют отдельной provenance и здесь не объявляются атомарными.

## Backend: все штатные cron jobs

`backend/lib/index.js:9–20` загружает `cronjobs` до `common.configManager.load()`, после запуска CLI и HTTP устанавливает `setInterval(cronjobs.run,1000)`. `cronjobs.js:14–35` содержит полный список ниже; отсутствующий timestamp равен нулю, поэтому каждый job может стартовать уже при первом вызове, независимо от указанного периода. `run` не ожидает возвращаемые promises: несколько jobs и их завершение могут пересекаться с hold и между собой. Период не является гарантией, что вначале будет тишина.

| Job | Записи и влияние |
|---|---|
| `roomsForceUpdate` | `cronjobs.js:178–190` читает active rooms, добавляет комнаты в `activeRooms` через `backend/lib/utils.js:311–316` и пишет `rooms.nextForceUpdateTime`; прямое изменение набора комнат следующего шага. |
| `genPowerBanks` | `:194–242` меняет `rooms.powerBankTime`, при наступлении срока вставляет `rooms.objects` powerBank и активирует комнату. |
| `genInvaders` | `:245–311,377–439` при выполнении условий вставляет NPC creeps, меняет `rooms.invaderGoal` и `rooms.objects` источников (`invaderHarvested`), активирует комнату. |
| `genDeposits` | `:557–640` при условиях вставляет deposit в `rooms.objects` и активирует комнату. |
| `genStrongholds` | `strongholds.js:29–127,130–237` создаёт структуры, меняет контроллер и активирует комнату; вызывается из `cronjobs.js:24`. |
| `expandStrongholds` | `strongholds.js:238–255,287–328,337–347` меняет поля core, создаёт новый объект и активирует комнату; вызывается из `cronjobs.js:25`. |
| `recreateNpcOrders` | `cronjobs.js:38–119` читает терминалы `rooms.objects`, меняет `market.orders` и `rooms.nextNpcMarketOrder`; нет прямой записи обязательных полей, но рынок/room metadata могут влиять на дальнейшее исполнение. |
| `sendNotifications` | `:124–171` изменяет notifications и `users.lastNotifyDate`; не пишет обязательные поля, но отдельный writer и возможная внешняя отправка. |
| `purgeTransactions` | `:443–467` удаляет transactions; не обязательное поле, но влияет на будущие runtime data. |
| `calcMarketStats` | `:472–520` перезаписывает market.stats; не обязательное поле. |
| `deletePowerCreeps` | `:533–551` удаляет users.power_creeps и меняет users.power; не обязательное поле в текущем контракте, но влияет на будущий runtime. |

В коде этих штатных jobs не найден прямой setter `memory:<userId>` или `gameTime`; это ограниченный вывод по перечисленным путям и установленным модам, не утверждение о произвольных модулях. Содержимое mods должно фиксироваться и проверяться: мод может добавить или заменить job. Backend при startup отдельно вызывает `utils.reloadBotUsers` для каждого configured bot (`backend/lib/index.js:21–23`, `utils.js:271–293`), переписывая `users.code`; в factory задан `bots:{}`, что устраняет этот штатный путь при условии отсутствия модифицирующего мода. CLI `system.runCronjob` может вручную вызвать job; API/CLI, websocket, внешние клиенты и тестовый setup с правом записи являются независимыми писателями и должны быть исключены из hold, кроме явно зарегистрированных read-only запросов. HTTP loopback не является блокировкой доступа.

## Нештатные и отложенные пути, которые нельзя устранить только cron

- `engine/src/processor.js:491–518` добавляет bulk objects/users/flags и event log в `resultPromises`, но `driver.activateRoom(roomId)` на `:504–505` **не** добавляет promise в этот список. Она пишет `activeRooms` (`driver/lib/index.js:176–177`), и теоретически может завершиться после `processRoom`, `markDone` и ACK. История на `:506` также detached и не является доказательством завершения. Процессор на `:579–585` ловит ошибку и всё равно может очистить intents и отметить задачу; только наличие `finish`/queue done не подтверждает успешное сохранение. Это конкретный кандидат гонки, а не экспериментально измеренная задержка.
- Runner сохраняет Memory и intents с ожиданием `q.all` (`engine/src/runner.js:32–47`); `driver/lib/index.js:153–159,180–242` пишет Memory в env и intents в БД с awaited activation. Но `runner.js:15–16,73–75` обрабатывает ошибку и может отметить done; требуется успешная запись конкретного пользователя и проверка ошибок, а не один счётчик очереди. Отдельные console/error-уведомления на `:23–27` не awaited и не доказывают состояние Memory.
- `driver/lib/index.js:170–173` получает `activeRooms` через `smembers`, затем отдельно удаляет ключ; пара операций не атомарна относительно стороннего `sadd`. `main.js:26–75` ждёт очереди и два commit, затем инкрементирует `gameTime` через `driver/lib/index.js:416–418`. Очередь storage (`storage/lib/queue.js:25–104`) в памяти: fetch перемещает pending→processing, markDone удаляет, reset очищает обе; `whenAllDone` означает отсутствие этих элементов, а не отсутствие detached RPC. Watchdog `engine/src/main.js:19–23` вызывает reset, если не отключён/переосмыслен исследовательским scheduler; проверять fault отдельно, без ложного ACK.
- `engine/src/main.js:77–87` запускает `updateAccessibleRoomsList` и `updateRoomStatusData` без await, а затем `roomsDone`. Они пишут env `accessibleRooms` и `roomStatusData` (`driver/lib/index.js:490–523`), а не четыре обязательные группы выше; эти данные влияют на последующий runtime и поэтому требуют отдельного отслеживания, если входят в fixture/snapshot. Источник ошибки roomStatusData при первом запуске уже наблюдался; initialisation должна предшествовать runtime и подтверждаться readback.
- `storage/lib/db.js:295–315` каждые 10 секунд удаляет просроченные env keys. `setex` и `expire` могут назначить expiry (`:582–605`). В исследуемых driver/backend путях `memory:<userId>` и `gameTime` сохраняются обычным `set`, но нельзя считать ключи неистекающими без проверки expiration metadata seed, модов и всех операций; `ttl == -1` трактуется по реализации осторожно, поскольку оно также означает истёкший/отсутствующий expiry (`:614–620`). Autosave Loki (`db.js:14–28`) пишет файл по таймеру и не является согласованным логическим снимком; stale disk DB после быстрого stop не доказывает содержимое памяти storage.
- Launcher автоматически перезапускает завершившиеся дочерние процессы и периодически runner/processor (`launcher/lib/start.js:112–132,174–198`); рестарт/потеря процесса во время hold — invalid/UNKNOWN до новой калибровки. Взаимодействие drain с потерей RPC, таймаутами и повтором требует fault probes. `storage/lib/queue.js:107–109` сам таймер ничего не пишет.

## Узкий вариант test-only и проверка

Предлагается исследовать в **собственном** моде, загружаемом при `configManager.load`, после проверки маркера экземпляра и роли backend, замену `config.cronjobs` на пустой объект до запуска интервала. `backend/lib/cronjobs.js` уже импортирован до этого и `run()` каждый раз читает `config.cronjobs` динамически, так что штатный список должен перестать исполняться; `system.runCronjob` также не найдёт имена. Проверить это по собственным версиям/хешам и order загрузки, запретить неизвестные моды, фиксировать набор отключённых jobs и FAIL при отсутствии ожидаемой формы/версии. Мод не меняет пакет на диске и не отключает runner, processor, игровой main или обычные игровые действия. Это изменение среды, а не доказательство её равенства обычному серверу; сценарии, зависящие от NPC/cron, такой режим не покрывает.

При первом цикле секундного таймера после старта проверить отрицательными probes, что ни один штатный cron не вызван (включая намеренно готовые к запуску условия), `activeRooms` и релевантные объекты не меняются в длинном hold; контроль без отключателя должен обнаружить `roomsForceUpdate`/подготовленную запись. Проверить отсутствие pre-existing in-flight jobs до входа в hold, повторный запуск и потерю процесса, запрет ручного `runCronjob`, readback включённого режима и отсутствие скрытых добавлений job. Никакого обещания, что elapsed time сам доказывает отсутствие отложенной работы.

Отдельно инструментировать или явно учитывать и ждать **все** promise `activateRoom` процессоров, включая rejection и конкретные room/step IDs, прежде чем выдавать barrier; необходимы fault injection с задержанной и отвергнутой операцией, worker crash и проверка no missed/double ticks. Не привязывать admission к одному стабильному snapshot или к неизменности числа queuedRooms: само число может законно меняться вследствие предыдущих intents/активации. Сверять набор и происхождение каждого room ID и инварианты after-drain. Доказать отсутствие expiry обязательных env keys и неподконтрольных writers/clients на протяжении hold; для остальных полей явно указать ограничение. Без этой калибровки даже корректное отключение cron не разблокирует HAR и не доказывает атомарность DB/Memory.
