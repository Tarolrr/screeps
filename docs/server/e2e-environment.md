# Одноразовая среда исследования E2E-SRV

Это исследовательский Linux-only lifecycle для отдельного сервера, не admission потиковой наблюдаемости и не замена исследованию scheduler. Код: `e2e/server/instance.js`. Пользовательский `~/screeps` используется только как источник установленных пакетов; его конфигурация, база, сокет и логи не читаются и не изменяются. Код не копирует live world или секреты.

```js
const {createIsolatedServer} = require('./e2e/server/instance');
const s = await createIsolatedServer({runId: 'probe', httpPort: 32141, cliPort: 32142, mods: []});
try {
  await s.start();
  await s.assertIdentity();
  // Только свой CLI: s.cliOptions; последовательность шагов определяет отдельный протокол.
} finally {
  await s.stop();
  await s.destroy();
}
```

Использовать Node 22 (`~/.local/node22/bin/node`) и явные разные свободные непривилегированные порты; 21025/21026 запрещены. Factory создаёт непредсказуемый каталог `e2e/server/.runs/<runId>-*` с правами 700 и `ownership.json` с токеном, абсолютным root и портами; содержимое каталога, включая маркер и любые журналы, не публиковать. Владелец handle обязан сохранить его до cleanup; восстановление после потери процесса или identity не реализовано: оставить каталог на карантине и остановить работу. `destroy()` отказывается работать до `stop()` и при несовпадении identity; при ошибке cleanup нельзя объявлять PASS. Маркер не является распределённой блокировкой scheduler и не защищает от программ, игнорирующих протокол. Один контроллер должен владеть конкретным handle; одновременные вызовы его операций отклоняются, а не выполняются параллельно. Сроков автоматического takeover нет.

Launcher использует свою группу процессов; до остановки проверяются PID, start time, группа и маркер. При запуске проверяются порты, свободная память host и доступный бюджет cgroup v2 (по умолчанию минимум 1 GiB), а также принадлежность обоих слушающих сокетов и конкретного принятого CLI соединения этой группе через `/proc`. Маркер заранее помещается в собственную seed DB; первое CLI выражение только читает его после проверки peer, затем проверка peer и listener повторяется. Команда записи в неизвестный сокет при bootstrap не отправляется. Это уменьшает риск гонки после проверки порта, но не резервирует порты до bind; несовпадение останавливает только свою группу. Гарантированное восстановление после SIGKILL координатора, недоступного `/proc`, PID reuse или потери маркера не реализовано: такие случаи — quarantine, не удалять и не убивать неизвестные процессы. Настраиваемый memory threshold — нижний порог, а не резервирование; нельзя обещать отсутствие OOM при конкурентной нагрузке.

В собственном каталоге генерируются `.screepsrc`, `mods.json`, `db.json`, логи, assets и относительный `storage.sock`. База строится из **пакетного** `@screeps/launcher/init_dist/db.json`, а не пользовательской: удаляются демонстрационные аккаунты и весь их код, оставляются только системные NPC IDs 2/3 и нейтральные source/mineral/controller без владельца/резервации; доступность комнат и пригодность фикстур ещё нужно калибровать. Снимок пакета не является пустой базой без системных данных. Ссылки на node_modules запускают установленные пакеты без их изменения, нативный ABI следует проверить при смене Node. `mods` принимает существующие абсолютные файлы, выполняемые во всех процессах сервера; только доверенные локальные тестовые модули. Необязательный `preload` — абсолютный путь к существующему доверенному файлу; его realpath задаётся через `NODE_OPTIONS --require` только собственной группе процессов, произвольный родительский `NODE_OPTIONS` не наследуется. Factory не удостоверяет hash или безопасность этого кода: проверка pinned версии и содержимого остаётся за вызывающим исследованием. Передаются `SCREEPS_E2E_ROOT` и `SCREEPS_E2E_MARKER`; `root/step-control` зарезервирован для отдельного тестового scheduler mod.

Установленный backend без ключа пытается использовать отсутствующий greenworks. Только для этой одноразовой среды создаётся локальный `offline-steam.js`: он заменяет в памяти `steam-webapi.ready` на немедленный callback, а `STEAM_KEY` получает фиксированный не секретный placeholder. Пакеты на диске не меняются. Это обход запуска backend, **не работающая Steam-аутентификация**: регистрация, вход через Steam и клиентские auth-сценарии не поддерживаются и не проверяются; не посылать auth-запросы. HTTP и CLI слушают loopback, сервер не предназначен для реальных пользователей. Нет гарантии отсутствия сетевой активности от остальных модулей; для строгой сетевой изоляции нужен отдельный network namespace/firewall и проверка.

Проверка без запуска сервера и полная проверка lifecycle (полный запуск требует отдельного бюджета памяти и отсутствия параллельного тестового сервера):

```sh
~/.local/node22/bin/node e2e/server/instance-lifecycle.test.js --offline
~/.local/node22/bin/node e2e/server/instance-lifecycle.test.js
```

## Потеря результата команды контроллера

`~/.local/node22/bin/node e2e/server/step-disconnect-probe.js` запускает отдельный экземпляр с отключённым backend cron и намеренно задерживает `activateRoom`. При deadline 100 мс команда получает UNKNOWN; тот же `StepClient` отказывает в следующей команде, а новый контроллер не может повторно опубликовать уже существующий `command-1`. Проверяются поздний ACK 1, единственный переход `gameTime`, один runtime счётчик и отсутствие `command-2`. Процесс сервера останавливается, каталог сохраняется на карантине даже при ожидаемом исходе. Это проверка файлового транспорта и потери результата команды, а не сетевой TCP disconnect или доказательство crash-recovery. Длинная задержка, ошибка cleanup или отсутствие позднего ACK приводят к ошибке с сохранением артефакта; запрещено возобновлять работу в этом экземпляре.

Этот опыт не доказывает безопасного восстановления после смерти контроллера и не подтверждает fence в целом.
