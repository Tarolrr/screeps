# Аудит dist2 для проектирования минимального модульного e2e

Область: собственные модули `dist2/`, существующие `dist2/tests`, `e2e/README.md`, `e2e/test7-user-dist2.js`, `e2e/dist2-deep-xfail.js`. Это аудит исходника, не новый эксперимент: сервер не запускался. Исторические наблюдения явно помечены ниже. Цель — создать задачи на тесты, а не исправлять стратегию. Здесь «красный» означает невыполненный функциональный контракт, известный дефект сохраняется отдельно как expected failure с причиной; XPASS требует пересмотра, а не автоматического игнорирования.

## Карта и границы

- `dist2/main.js:1-58`: загрузка mapPatch, регистрация четырёх типов, load и initialize в порядке build → source → spawn → room; затем каждый тик роли → source → spawn → room → build → save, исключение перехватывается и прекращает остаток тика. Инициализация вне try. `js-yaml` импортирован (`:14`), активных вызовов и конфигурационного пути нет: vendor `dist2/js-yaml.js` исключить из собственного функционала, но проверить, что загрузка с этим импортом работает и что активный consumer не появился. Комната без спавна пропускается контроллерами.
- `SourceController.js:12-50` создаёт source и harvester для каждого источника в комнате со спавном. `RoomController.js:11-103` создаёт по источнику mule для спавна, mule для контроллера и upgrader; `BuildController.js:18-85,104-173,176-233` создаёт builder, строительных mule для существующих source ресурсов, три extension-заказа и дороги; reconcile каждые 100 тиков, обработка сайтов перед повторным apply. Из-за порядка initialize строительный mule появляется только на последующем reconcile. При недоступном объекте source обращение к `source.id` риск исключения.
- `SpawnController.js:8-139`: каждые 10 тиков очистка Memory отсутствующих крипов; восстановление active при смерти/подходе expiry и spawning без процесса; завершение/сбой процесса; группировка pending по комнате, первый спавн, сортировка по убыванию, только первый заказ, даже при ошибке/недостаточном body. Энергобюджет до active пары harvester+mule_spawn — SPAWN_ENERGY_CAPACITY, затем capacity комнаты; фактическая доступная энергия отдельно влияет на ответ движка. Имя включает annotation и `Game.time % 2`. `utils.priority.js:1-8` использует последние шесть hex-символов id ×100 минус offset; проверить порядок, равенство и невалидный id как контракт исходника, а не предполагать удобные малые приоритеты.
- `resourceManager.js:11-98,124-160`: регистрация, восстановление экземпляров, apply по annotation, update spec без обнуления state, выборка/удаление, ID по времени и счётчику; save с `disabled=true` или строкой `true`, при повторном включении load перед save. `resources.Resource.js:18-83,84-185`: типизированная проверка известных полей (отсутствующие допускаются), сравнение spec через JSON, сериализация и hooks. Неизвестный тип создаёт plain object, но повторный apply ожидает `matchesAnnotation`: сомнительный контракт. Счётчик ID не сохраняется. `resources.sourceResource.js:1-35` связывает id с Game; `resources.creepOrder.js:1-139` хранит state и генерирует постоянные части и целые наборы ratio с maxCost, без явного лимита 50 частей; `resources.spawnProcess.js:1-80` по доступности spawn и creep переводит spawning в completed/failed. Точные строки каждого файла независимы от нумерации в этом абзаце.
- `resources.constructionOrder.js:27-100,103-152,154-252,254-272`: генерация позиций, фильтрация terrain/объектов, claim/validate построек, выбор отсутствующих sites, удаление лишних при изменении spec, сериализация. Конструктор сбрасывает флаги wrong-type/wrong-position даже при reload; `enabled` в схеме, но не применяется. Несовместимость экспорта/вызова patterns делает основную генерацию недостижимой в текущем коде. `BuildController.js:196-217` ограничивает до пяти sites и учитывает только OK, не сохраняя ответ/причину; builder ожидает `order.constructionSites`, которое order не заполняет (`role.builder.js:119-149`), поэтому приоритет sites не связывается с заказами.
- `constructionPatterns.js:29-95,97-248,250-415`: реестр single/checkboard/line/ring/rectangle/parallelLines/path/patternPlacer экспортирован как `{patterns}` с экземплярами. Отдельный прямой вход к экземпляру позволяет исследовать иначе недостижимые ветки на настоящем terrain/Game. Индексный вариант центрирует выбранное подмножество; direction line и filled rectangle фактически не используются. Path проверяет room после `room.getTerrain()`, передаёт остальные поля непосредственно в findPath, вычисляет смещения и фильтрует стены; placer сканирует 2500 точек и проверяет строковый индекс terrain, тогда как вызывающий передаёт объект terrain. Эти особенности — факты кода; ожидания геометрии и стоимости CPU нужно подтвердить экспериментом.

- `mapPatch.js:1-15`: добавляет Map.fromObject/toObject/filter и переопределяет Array.flat; toObject присваивает не объявленную `result`, flat без initial value и фактически не разворачивает массив при depth=1. `logger.js:1-65`: уровень загружается из Memory на каждом loop, singleton при создании записывает дефолт только при отсутствии loggerState; setLevel сам не сохраняет изменение. Проверить фильтрацию и reload как наблюдаемые вспомогательные контракты.
- `dist2/tests/BuildController.test.js`, `dist2/tests/resources.constructionOrder.test.js`, `dist2/tests/mocks/screeps.js` — mock/unit, не доказательство результата движка; `dist2/example.md`, `rearch.md`, `llm-helper.md`, `patternVisualizer.html`, `mock-game.js` — примеры/историческое проектирование или локальная визуализация, не production entrypoint. Сравнение каталогов выявляет различия в `BuildController.js`, `constructionPatterns.js`, `main.js`, `resources.constructionOrder.js`; остальные общие файлы совпадают с исторической инструментированной копией (удалена).

Исторически подтверждено в `e2e/README.md` раздел dist2 deep-dive: пустые positions из-за формы экспорта; после диагностического исправления — вызов экземпляра как функции; после следующего исправления вложенные road `opts` не применялись и путь отсутствовал; после расплющивания были 70 позиций и 5 sites; terrain mismatch мешал extension. Исторический test7 подтверждал лишь spawn и отсутствие ошибок; deep test отдельно наблюдал upgrade, но не стройку. Ни одно из этих наблюдений не является новым подтверждением в текущем окружении.

## Общий протокол каждого сценария

Отдельный выделенный сервер и очищаемая комната: зафиксировать исходный снимок, owner/reservation, terrain, source/controller, объекты, глобальные настройки тика; уникальный пользователь, имена и annotation на сценарий, никакого параллелизма в комнате. Setup задаёт стартовые объекты и энергию, но не подменяет проверяемый результат: нельзя вручную положить готовую дорогу или подправить Memory, чтобы обойти генерирование/переход под тестом. Для изолированных сценариев допускается начальная фикстура заказов, тела, позиции и Memory как вход, а test entrypoint вызывает **реальный неизменённый** production модуль с реальными Game-объектами; также обязателен отдельный непропатченный `main.loop`. Зафиксировать хеши загруженных production модулей и сравнить с репозиторием; измерительная обвязка не переписывает функции и возвращаемые значения. Если сценарий тестирует создание ресурса/переход, соответствующее состояние нельзя внести фикстурой.

До запуска требуется экспериментально доказанный fence и quiescence всех писателей согласно server-research.md; иначе per-tick наблюдение BLOCKED, polling недостаточен. На каждом игровом тике собирать отметку Game.time, снимок `rooms.objects` (id/type/owner/позиция, store, source energy, creep body/spawning, actionLog, site progress/progressTotal, структура и controller progress), проекцию `Memory.creeps`, `Memory.resourceManager`, ошибки/уведомления, при необходимости результаты реального вызова через отдельную диагностическую Memory. Сопоставлять идентификаторы и изменения по тикам; отсутствие ошибок, наличие крипа и естественное +1 energy спавна не являются доказательством передачи/стройки. Сохранять временной ряд и последний снимок при таймауте. Границы для непроверенных engine-механизмов задавать измеряемыми параметрами B_move, B_spawn, B_action, B_reload и B_path, вывести из размеров мира и экспериментальной калибровки, записать значения в результат; не выдавать их за уже подтверждённые. Явные периоды 10/100 — из исходника; к ним прибавить необходимые B. Проверять положительные изменения и отрицательные инварианты, а также нормализованные причинные инварианты между независимыми запусками с отображением seed, времени и фактических ID; побайтная детерминированность не предполагается без доказательства. В finally сначала восстановить длительность тика, затем удалить тестового пользователя и все созданные объекты/нейтральные постройки по снимку, восстановить другие настройки и проверить очистку. При аварии фиксировать незавершённую очистку, а не объявлять успех.

## Минимальные семейства сценариев

Каждая строка — независимый сценарий с собственной фикстурой и очисткой по протоколу. Везде ограничение — указанный период плюс калиброванные B; если движок недоступен или граница не установлена, результат blocked/исследование, не PASS. Состояния до и после intent наблюдать на последовательных тиках, поскольку отложенное применение движком требует подтверждения.

### A. Сквозной цикл и изоляция

1. **Полный pipeline.** Пустая принадлежащая комната: один source, controller, spawn с достаточной энергией, свободная достижимая местность, без крипов и sites. Загрузить production main; наблюдать initialize и минимум 100+10+B_spawn+B_move+B_action тиков. Проверять в Memory source/creep/road/extension заказы, порядок и state pending→spawning→active, body и реальные harvest→drop→pickup→transfer или drop около назначения, изменение progress контроллера; следить за position/store каждого участника. Отрицательно: чужих заказов/крипов нет, естественный прирост спавна не считается доставкой. Для стройки обязательны отдельные условия ниже; пустые positions/no sites — known-defect RED, даже если spawn/upgrade есть. Пропущенный save после ошибки фиксировать отдельно.
2. **Reset/reload.** Та же контролируемая комната, получить заказы и хотя бы один state через настоящий loop, сохранить снимок, принудительно перезапустить runtime/module cache без изменения production и дождаться B_reload+100 тиков. Идентичные annotation не дублируются, state/order/связь с реальными объектами корректно переживают JSON round-trip; сравнить DB и Memory до/после, проверить отсутствие повторного спавна активного заказа. Затем отдельный запуск с пустой Memory проверяет повторную инициализацию. Ошибки загрузки и потеря state — RED.

### B. Resource и spawn

3. **CRUD/serialization.** Настоящий entrypoint регистрирует production классы в комнате со spawn/source; apply annotation дважды, затем меняет spec при существующем состоянии, save, reload, lookup и delete. По каждому тику сравнить id, spec/state, тип/поведение экземпляра после JSON, absence дубликата, выборки и отсутствие удалённого. Отдельно unannotated ID и неподдерживаемый тип, недопустимое поле/тип и отсутствующее поле; исключение документировать как фактический контракт. Завершить за B_reload+B_action.
4. **Disabled и восстановление.** Создать ресурс через apply; установить управляющий `Memory.resourceManager.disabled` в true, затем строку true в независимом прогоне, изменить ресурс через API и проверить по тикам, что сериализованный набор не перезаписан; выключить флаг, проверить load исходного состояния перед save. Сравнить с false, не спутать in-memory и сохранённое; B_reload+B_action.
5. **Очередь/ограничения.** Комната со spawn, источником и вручную заданными независимыми pending заказами с различным priority, schema/body и свободными именами, заранее без active пары. На ближайшем тике, кратном 10, проверить выбор высшего, постоянные части, ratio/maxCost, цену и `spawn.spawning`/order/process; затем окончание и active за B_spawn+10. Варианты: spawn занят; энергии меньше стоимости; highest не собирает body или spawnCreep возвращает ошибку (например, занятое имя); нижний заказ не запускается — текущий факт, функциональное ожидание обхода отдельно обозначить как вопрос контракта. Проверить отсутствие лишнего процесса/расхода при неуспехе. Независимо создать реальными переходами active harvester и mule_spawn одного source и проверить переключение бюджета на capacity, затем отсутствие пары. Две комнаты и два спавна в одной комнате выявляют группировку и выбор только первого.
6. **Жизненный цикл spawn.** Реальным spawn получить process и завершение; отдельные контролируемые случаи удалить/дождаться смерти крипа или спавна, создать spawning-заказ без процесса и приблизить expiry входной фикстурой. На ближайших 10-tick reconcile проверить pending/active, creepName, expiry, удаление process и старой Memory.creeps, отсутствие ложного active; ограничение 10+B_spawn+B_action. Проверить failed и повторную попытку в следующем окне, не считать одно лишь исчезновение процесса успехом.

### C. Роли и ресурсы на земле

7. **Harvester.** Один доступный source и крип WORK/CARRY/MOVE с пустым store в нескольких клетках, sourceId валиден. За B_move+B_action наблюдать сокращение дистанции, снижение энергии source, рост store, затем при полном store падение энергии рядом и опустошение; сверить DB и Memory. Отдельно отсутствующий id/пустой source и spawning-крип: нет несанкционированной добычи/исключения; ждать ограниченное окно B_action.
8. **Mule.** Независимые варианты entity и area: рядом контролируемая куча или container с энергией, цель — spawn/extension с известным свободным объёмом, ground у controller либо дружественный creep с выбранной ролью. CARRY/MOVE, шаблоны в Memory, пустой store, расстояние >1. За B_move+B_action наблюдать idle→collecting, фактический pickup/withdraw, полный store→delivering, движение, transfer/drop и обратный переход; сравнить потери/прирост с естественной генерацией и decay, зафиксировать actionLog и индекс задачи. Варианты: ближайшая из двух целей, фильтр типа/роли, пустая/полная/отсутствующая цель, отсутствующие шаблоны и несколько задач; отрицательно — нет передачи неподходящему объекту и продвижения индекса без OK. Место ground и энергия — вход, но доставка должна создаться реальным кодом.
9. **Upgrader.** Реальный принадлежащий controller, WORK/CARRY/MOVE, пустой store, энергия на земле в радиусе 5 контроллера; отдельно container в радиусе 5 крипа без ground. На последовательных тиках idle→collecting, pickup/withdraw, полный store→upgrading, движение в range и рост controller.progress при уменьшении store, затем collecting; B_move+B_action. Проверить приоритет ground перед container, отсутствие доступной энергии и отсутствие controller как отдельные негативные случаи, не считать лог без ошибки доказательством upgrade.
10. **Builder.** Для изоляции роли допустим site как вход фикстуры, но не готовая постройка: WORK/CARRY/MOVE, куча энергии у spawn, доступный road site с известным progress, collectTemplates. За B_move+B_action наблюдать IDLE→COLLECTING, фактический pickup, полный store→BUILDING, targetSiteId, перемещение, рост progress и завершение в реальную структуру; сверить энергию и отсутствие прежнего site. Отдельно без site, без task, исчезнувший target и два sites на разных дистанциях/приоритетах: проверить переход в idle и новый target, зафиксировать отсутствие реально заполненной карты order.constructionSites как дефект приоритетов. Не считать установку site завершением строительства.

### D. Геометрия и строительство

11. **Patterns на настоящем мире.** Отдельный production entrypoint вызывает зарегистрированные экземпляры single/checkboard/line/ring/rectangle/parallelLines, path и patternPlacer на реальном room/terrain; открытая площадь, край комнаты, стены и swamp, source/spawn/controller с известными координатами. Для каждого независимого варианта сохранить список/index/outOfBounds и сравнить с ожидаемыми координатами, границами и отсутствием стен; проверить неизвестный pattern, индекс после конца, direction/filled и повторяющиеся позиции. Path сравнить с достижимым маршрутом, непроходимой целью, width 1/2, настройками range и отсутствующей room; не объявлять конкретный маршрут движка нормативным без фиксации версии. Terrain объект и wall внутри bounding box проверяются отдельно. Ограничение B_path с записью CPU/таймаута. Это тест доступного API экземпляров, не подмена поведения order.
12. **Order → site → completion.** На пустой свободной площадке принадлежащей комнаты source/spawn/controller, через настоящий BuildController создать заказы и вызвать reconcile на кратном 100 тике; наблюдать positions в Memory, DB sites с координатами/типом, лимит пять, затем с реальным builder и энергией — progress и completed структуру, после очередного reconcile — ownedStructureIds без повторного site. Сравнить дороги к source/controller и extension, отрицательно — стены, занятые несовместимые клетки, >5 sites и дубли. Срок 100+B_path+B_move+B_action плюс следующее окно 100. Текущий экспорт patterns приводит к пустым positions: основной сценарий RED/known-defect, не разрешается заранее создавать road/site для обхода генерации. Отдельный сценарий роли builder с site как входом уже описан выше.
13. **Ошибки, пересчёт и retry.** Через production order/controller независимо воспроизвести ограничения движка: недоступная комната/клетка, лимит RCL или global sites, несовместимый объект, существующие совместимые road/rampart, уничтоженная ранее claimed структура, изменение type/positions/count и удаление лишнего. Фиксировать реальный return code и DB на каждом reconciliation, при снятии препятствия проверить повторную попытку в следующем окне 100; не предполагать retry по одному отсутствию ошибки. Текущий дефект генерации может блокировать последующие проверки: сообщить blocked вслед за known-defect, а не подменять результат positions. Отдельный прямой вызов методов order с допустимой входной фикстурой может проверить claim/validate/remove и failure destroy, сохранив полную цепь отдельной. Ограничение 2×100+B_action; проверять, что чужие/правильные структуры не удалены.

### E. Вспомогательные контракты

14. **Приоритеты и logger.** Контролируемые source id с различными последними hex-цифрами: проверить реальные численные priority harvester и mule_spawn, сравнить сортировку с фиксированными 40/49/50/51/70/80/1000, включая равенство и невалидный id в изолированном вызове; затем показать выбор spawn или site по данным очереди. Изменить Memory.loggerState.currentLevel и на следующем loop подтвердить фильтрацию console, включая невалидный уровень и runtime reload; за 10+B_action. Отрицательно — не трактовать порядок логов как реальный порядок действий.
15. **mapPatch.** В отдельном runtime вызвать production patch и проверить Map.fromObject/toObject/filter, обычный и пустой массив на flat depth 1/2, глобальную переменную `result` и сохранение значений после JSON/перезагрузки там, где применимо; не использовать polyfill тестовой обвязки как oracle. За B_reload+B_action; несовпадения стандартной семантики фиксировать как дефект, а не подстраивать ожидания под код.

Эти семейства специально объединяют много независимых вариантов, а не создают тест на каждый файл. Любая недостижимая через main ветка помечается как таковая; прямой вызов подтверждает только её локальное взаимодействие с движком, а сквозной сценарий остаётся отдельным. Для каждого результата сохранять версию сервера, hash модулей, фикстуру, параметры B, временной ряд, итог cleanup и классификацию PASS/RED/known-defect/BLOCKED.
