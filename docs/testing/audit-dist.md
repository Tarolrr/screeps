# Аудит `dist`: карта поведения и спецификация модульных e2e

Срез исходников, не результат запуска сервера. Граница доказательств: ссылки на файлы и строки ниже подтверждают существующий JavaScript; движение, отложенное применение intent, скорость добычи, decay, регенерация spawn/source и точный формат серверной БД требуют проверки на используемой версии движка. Исторический `e2e/test6.js` проверяет только появление хотя бы одного creep и отсутствие уведомлений об ошибках; `main` сам перехватывает исключения (`dist/main.js:19,53`), поэтому такой критерий не доказывает цикл экономики или отсутствие ошибок в логах. Никаких новых live-результатов здесь не заявлено.

## Инвентарь и достижимость

`main.loop` (`dist/main.js:1-56`) загружает mapPatch и роли, инициализирует `creepId` и `managers` только при отсутствии первого, затем для каждой видимой комнаты создаёт и запускает RoomManager, после чего вызывает роль каждого creep по `memory.role`. Общий catch прерывает остаток тика. Не фильтрует комнаты по владению или наличию spawn. Порядок менеджеров ниже существенен: intent роли и сохранение менеджеров происходят в разное время.

| Модуль | Экспорт и фактическое поведение; доступность |
|---|---|
| `main.js` | `loop`; основной путь выше. Старые три планировщика импортированы, вызовы закомментированы. |
| `RoomManager.js` | класс; создаёт spawn, storage, controller, source по каждому source и delivery; добавляет маршруты на первом запуске; run: spawn → sources → storage → delivery → controller → очередь по наибольшему priority → save (`:11-106`). ConstructionManager не подключён. |
| `Manager.js` | базовый класс, `features` пустой Set, `planDelivery` no-op, абстрактные методы бросают. Достижим через наследование. |
| `CreepOwner.js` | класс: сохраняет имена живых и queued, load отбрасывает отсутствующих, addCreep вызывает одноимённый метод менеджера, run переносит появившихся queued в живые (`:1-37`). |
| `SourceManager.js` | класс и `cache` (обращение в конструкторе не записывает значение); свободные соседние terrain клетки, needWork=ceil(capacity/300/2), учёт harvesters, при потребности priority 5; rate пропорционален work; destination — наибольшая куча рядом либо wait 10; контейнер не выдаётся; getter availableEnergy вычисляет поле, но не возвращает (`:10-171`). |
| `SpawnManager.js` | класс; очередь, первый spawn, приоритет маршрута 6, цель сначала незаполненный spawn, затем extension, иначе wait; queueCreep вычисляет шаблон и специальные первые `harvester0`/`mule1` по 150; run удаляет queued-владельцев вне очереди, dryRun и spawn первого (`:10-165`). |
| `DeliveryManager.js` | класс и cache; маршруты по классам producers, сортировка по убыванию priority, матрица дорог/препятствий; расчёт mules, выбор первого подходящего маршрута по `src` и положительному `energyNeeded`, запись destination и plannedDeliveries; удаление завершённых и умерших (`:23-201`). |
| `StorageManager.js` | класс; позиция из spawn или флага `storage`, приём ground range 2, ресурсы и контейнеры в радиусе плюс pending, rate=floor(available/100), need=3000-available-pending; реально structure storage не учитывается (`:10-106`). Код после `return` в run недостижим. |
| `ControllerManager.js` | класс; ground range 2 около контроллера; available и need аналогично storage; заказывает upgrader если available/500 больше числа живых и queued (`:10-104`). |
| `ConstructionManager.js` | класс, в main недостижим; аналог controller, builder, очередь расширений; `load` присваивает queue в priority, `findExtensionPos` использует `pos` вне области видимости и `pos.t`, `queueExtension` затеняет переменную условия и может не завершиться (`:12-138`). Проверять изолированно с CPU/внешним deadline, не как успешное строительство. |
| `CreepPlanner.js` | класс `calculateCreep` и свойство `roles`: harvester MOVE+WORK, mule 2 CARRY+MOVE, upgrader MOVE+CARRY+WORK, builder MOVE плюс WORK/CARRY/MOVE:0.5, repairer MOVE плюс WORK/CARRY. Цена, efficiency/state и null при недостатке; fractional `new Array(0.5)` является возможной ошибкой (`:5-133`). |
| `creepUtils.js` | экспорты классов `CreepTemplate`, `QueuedCreep`, только поля данных. |
| `role.harvester.js` | `run`: spawning return; assignedSource через id, harvest или moveTo (`:4-14`). |
| `role.mule.js` | `run`: destination wait/resource/structure/ground, затем collect/store; collect при заполнении меняет state, иначе спрашивает source.destination; store при пустом завершает delivery и меняет state, иначе planDelivery (`:7-95,139-184`). Код после безусловного break на :184 недостижим. |
| `role.builder.js` | `run`: collect через контейнеры или кучу в радиусе 5 spawn; full→build; ближайший собственный site, build/move; empty→collect (`:4-45`). Роль достижима при наличии внешнего creep, автоматического заказа builder в main нет. |
| `role.repairer.js` | `run`: collect как builder; full→repair; ближайший structure с hits+1000<hitsMax и hits<300000; empty→collect (`:4-45`). Автозаказа нет. |
| `role.upgrader.js` | `run`: collect из первой кучи в радиусе 5 контроллера, full→upgrade, upgrade/move, empty→collect (`:4-27`). При отсутствии кучи ранний return даже после смены state. |
| `mapPatch.js` | побочные `Map.fromObject`, `Map.prototype.toObject/filter`, переопределение `Array.prototype.flat`; `toObject` пишет не объявленный `result`, flat depth=1 фактически не раскрывает вложенные массивы (`:1-15`). Используется доставкой и влияет глобально. |
| `Consumer.js` | класс абстрактного интерфейса, planDelivery no-op; импортируется, но менеджеры наследуют Manager, не Consumer. |
| `Producer.js` | `Producer` и `ProducerMixin`, абстрактные getter/методы; импортируются, но реальные менеджеры не наследуют mixin. |
| `logger.js` | singleton trace/debug/info/warn/error, load из Memory, конструктор save при отсутствии состояния, setLevel не сохраняет изменённое состояние (`:1-65`); main использует logger. |
| `EconomyPlanner.js` | класс, статические коэффициенты и run сбрасывает room.memory.economy и рассчитывает локальный total, не сохраняет его (`:1-29`); не импортируется main. |
| `SpawnPlanner.js` | класс static run; старый план по `srcDescs`, сбрасывает spawn.memory.queue; использует `CreepPlanner.roles.keys()` на обычном объекте (`:5-76`). Импортирован, вызов выключен. |
| `SourceDesc.js` | класс, считает клетки, needWork/needCarry/дистанцию, update и availableCarry (`:4-78`); старый planner, не текущий SourceManager. |
| `room.harvestPlanner.js` | объект run и assignHarvester/assignMule; раз в 100 тиков строит srcDescs и матрицу и назначает по старому полю `assigned_source` (`:3-109`); вызов main выключен. |
| `room.consumptionPlanner.js` | run каждые 50 тиков и assignMule, счётчики и dst spawn/cont/ctrl (`:1-95`); вызов выключен. |
| `room.pathPlanner.js` | run пустой и `assignMule` ссылается на пустой assignPath (`:1-12`); не импортируется main. |

Корневые `api-client.js`, `get-terrain.js`, `viz-server.js` и скрипты копирования — внешняя доставка/визуализация и tooling, не игровые переходы `dist`; их отдельные контракты не являются условиями успеха стратегии. Тестовая обвязка вправе использовать их только после отдельной проверки безопасности и версий. Дормантный код указан полностью для прозрачности; его запуск отдельным тестовым entrypoint не доказывает достижимость через main и не означает требования включить его в production.

## Дефекты и риски baseline, которые нельзя превратить в успешное ожидаемое поведение

* StorageManager.run деструктурирует результат `find` без проверки (`dist/StorageManager.js:102-105`): пустой набор флагов или набор без подходящего флага может бросить. Флаг в невидимой комнате может иметь `flag.room` undefined. Проверка с отсутствующим и неподходящим флагом — expected red до исправления.
* На переходе из spawn очереди в появившегося creep `SpawnManager.run` сначала фильтрует очереди владельцев по ещё находящимся в очереди spawn (`dist/SpawnManager.js:121-132`), затем SourceManager.run переносит queued в живые. При снятии из spawn очереди до появления creep привязка может потеряться. Проверить каждый тик через рождение и следующий перезапуск; не считать исчезновение ownership успешным.
* `availableEnergy` storage/controller уже содержит pending, а `energyNeeded` вычитает pending ещё раз. Проверить учёт одной доставки один раз как желаемый контракт и документировать красный baseline (`dist/StorageManager.js:75-100`, `dist/ControllerManager.js:76-101`).
* Отсутствующий spawn/неконсистентные Memory, потерянный объект destination, ошибки construction, некорректная дробная длина массива builder, отсутствие возврата source.availableEnergy, пустой или нулевой distance, `mapPatch` — отдельные воспроизводимые негативные кейсы.

## Общий протокол e2e

Использовать настоящие серверные Game/Room/Creep/Source/Structure объекты и исходные модули `dist`; тестовый entrypoint может вызывать один настоящий модуль для изоляции, но не патчить production. Отдельный сценарий обязательно вызывает неизменённый `main.loop`. Fixture — комната в отдельной одноразовой установке с собственными БД, socket, портами и scheduler, подготовленной по результатам server-research. Журналировать происхождение каждого созданного или исходного объекта и фактически выданные сервером ID; префикс run-id применять только к именуемым объектам, а не к серверным ID или нейтральным объектам. До и после каждого шага читать наблюдаемые DB и Memory с номером Game.time, ID, владельцем, типом, координатами, store, hits/progress, состоянием spawning и полями Memory. Снимать снимок до вызова и после применения intent; точный сдвиг snapshot относительно intent откалибровать на движке, не предполагать синхронное исполнение.

Базовый открытый terrain fixture: controller RCL 2 в (25,25), owned spawn (10,10), source S (15,10), пустые клетки маршрута; второй source (15,20) для изоляции назначения. Если штатная генерация не позволяет задать эти координаты/объекты, выбрать заранее проверенную эквивалентную комнату и записать фактические позиции и ограничения. Контейнер (16,10), ground pile (16,11), extension (11,10), site (12,10), ремонтируемая дорога (13,10), флаг `storage` (20,20) создаются только в сценариях, где перечислены. Энергия, состояние и source capacity задаются явно; тело тестового creep указывать и проверять по DB, в том числе активные части. Состояние начального Memory изолировать namespace/полным снимком, `creepId`, `managers`, room memory и creep memory задать явно. Каждый сценарий записывает seed, версию кода, tick T, ID, фактические настройки регенерации и снимки. Не использовать prebuilt site/structure или чужой объект как результат действия; сравнивать конкретный ID, owner, role, origin, координаты и дельты.

Для каждого действия проверять причинность: исходный объект существует и имеет нужное состояние на T; только испытуемый creep может выполнять действие в тестовой комнате; изменение соответствующего объекта и энергии creep согласовано с intent на T+1 или указанной измеренной границе. Spawn energy может автоматически восстанавливаться: прирост spawn сам по себе не доказательство доставки. Требовать уменьшения store конкретного mule и увеличения store именно цели в том же окне с контролем регенерации (или отключённой/измеренной регенерацией и отрицательным контролем без mule). Учитывать decay кучи, регенерацию source, стоимость spawn и engine intent conflicts; не требовать сохранения суммы без модели этих эффектов. Переходы Memory проверять на каждом тике, а не только конечный итог. Для каждого ожидания до запуска вывести верхнюю границу игровых тиков из проверенных для установленной версии движка длительности spawn для конкретного body, длины маршрута, terrain, fatigue, активных MOVE и остальных частей, доступности пути, периодов контроллера и задержек применения intent; явно добавить наблюдательные fences до и после действия. Если параметры или граница недоказуемы, сценарий заблокирован до калибровки на одноразовой установке. Отдельно задать wall-clock timeout по скорости тиков установки; отсутствие прогресса, ошибка в логах, CPU exhaustion или остановка тиков — FAIL с последним снимком. Не считать пойманное main исключение успехом.

## Минимальные параметризованные семейства

1. **Raw pipeline и restart.** Fixture: RCL2, source capacity зафиксировать, spawn 300/300, storage-флаг, Memory `{}`; T вызвать настоящий main, на каждом тике от T до вычисленной границы проверить инициализацию creepId, имена manager, маршруты и очереди, приоритет заказа, dryRun/spawn и соответствие роли/body/assignedSource, spawning→живой, source energy→куча и назначение владельца. Изолировать движковую длительность spawn по body, границы появления и движения вывести из подтверждённых констант и поведения версии движка, конкретных body, terrain, маршрута и измеренных fences, как описано в общем протоколе. На промежуточном тике сбросить глобальный модульный контекст без удаления Memory и продолжить; сравнить реконструированные routes/costMatrix/owner и продолжение экономического действия. Негативные варианты: флаг отсутствует, чужая видимая комната без spawn, creepId задан при отсутствии managers, умерший queued и неверный source; ошибка — expected red с трассой, не PASS. Проверять что фикстурный creep не удовлетворяет проверке создания нового. Данный сценарий обнаружит ограничения baseline и не заменяется тестом `test6`.
2. **Producer/планировщик и spawn.** В той же комнате отдельно вызвать реальный SourceManager/SpawnManager с настоящими объектами: T источник 3000 (или известная capacity), без harvesters; проверить workplaces по terrain, needWork, запрос priority 5 и assignedSource. Сравнить no-place, достаточный work, queued и умерший creep; на каждом тике freePlaces/hasWork и `Memory.managers`, body/стоимость/очередь/имя/creepId; повторить при энергии spawn 0 и полной, busy spawn, двух заявках. Контроль: с недостатком энергии нет нового spawn, после появления достаточной энергии ровно голова очереди рождается; учёт скорости/энергии не выводить из одной регенерации. Проверить `harvester0` и `mule1`, а также обычные шаблоны на достаточном и недостаточном бюджете; builder fractional baseline — expected red.
3. **Доставка как таблица маршрутов и конечных состояний.** Mule `[CARRY,CARRY,MOVE]` с известными 0/100 энергии; producer S, pile 100 в (16,11), spawn/extension не полные, затем storage/controller ground. На T проверить выбор src и priority, запись destination и plannedDeliveries `{amount,dst}`, на следующих тиках pickup, state collect→store, движение, transfer/drop, очистку destination и pending, возврат store→collect. Для resource/ground/structure/wait параметризовать отдельные destination, расстояние 1 и >1, пустую/исчезнувшую цель и wait time 2; сохранять каждый тик position, store, pile, structure store, Memory state/destination, pending и идентичность объектов. Для маршрутов без потребности или другого src — не назначать; при смерти mule pending очищается; при нескольких потребителях приоритет должен определять цель. Каждую фазу ограничить расчётной границей по body, terrain, маршруту, fatigue и подтверждённым intent fences; использовать контроль без mule и без допустимого маршрута. Проверить storage/controller pending ровно один раз как expected red baseline.
4. **Роли как одна таблица состояний.** Использовать настоящий вызов соответствующего role.run, собственный creep `[WORK,CARRY,MOVE]` с 0 или 50 энергии, источник/контейнер/падение/цель в радиусе 1, затем расстояние 4. Harvester: назначенный source, падение его энергии и появление добытого ресурса; неверный id и spawning — без добычи. Builder: site с незавершённым progress и container 50, collect→build и рост progress затем возврат в collect; отсутствие site/пустой container и чужой site — без ложного progress. Repairer: подходящая реально допустимая структура с подтверждённым в версии движка hitsMax, достаточным для соответствующего порога, например укрепление при разрешённом уровне контроллера: случаи hits+1000<hitsMax, равенства и hits=300000 создавать только после проверки допустимости типа, лимита, владельца и значения hitsMax; collect→repair, рост hits и расход энергии только допустимой цели. Upgrader: pile 50 у controller, collect→upgrade, прирост progress контроллера и расход энергии; нет кучи, пустой creep и spawning — отдельные ветки. Наблюдать state до и после каждого тика, поскольку intent применяются движком позднее; не требовать смены state на том же тике, когда pickup/расход только запланирован. Границу каждого случая вычислить по проверенным engine constants, body, состоянию fatigue, длине и terrain маршрута, периоду контроллера и intent fences; wall-clock ограничить отдельно. Убедиться, что на старте fixture site ещё не построен, hits/progress ниже цели и нужная роль уникальна.
5. **Изолированные границы/dormant.** Настоящий модуль вызывается test entrypoint: ConstructionManager при RCL1/RCL2 и фактическом лимите extension, пустой/существующий site, проверка создания валидной позиции и builder, ограничение CPU и wall-clock (дефекты выше expected red); источник без куч/с контейнером и двумя кучами; destination spawn/extension/wait; Map round-trip/filter и Array.flat на depth 1/2, сохранение/восстановление routes/costMatrix. Старые планировщики, SourceDesc, EconomyPlanner и pathPlanner проверить изолированно как отдельные API только если входят в согласованный контракт: периодические и непериодические тики, учёт assigned_source и dst, пустой path, расчёт distance/carry, отсутствие записи economy total. Они не покрывают main; ожидаемые ошибки задокументировать, не делать их эталоном успешной стратегии. Абстрактные интерфейсы и logger достаточно проверить контрактно без имитации полной игры.

Для всех семейств обязательна отдельная одноразовая установка с собственными БД, socket, портами и scheduler; общий пользовательский мир и его восстановление не являются допустимым fixture. Teardown останавливает только принадлежащие установке процессы и удаляет созданные ресурсы по журналу установки и фактическим ID, затем подтверждает отсутствие хвостов; сохранять достаточно диагностики для разбора сбоя. Фиксировать провалы setup/teardown отдельно; не запускать новые live-сценарии без явного согласованного безопасного окружения. Сценарии, которым движок не позволяет создать конкретный fixture, остаются заблокированными с причиной, а не зелёными.
