# Единое ТЗ: минимальное модульное e2e для dist и dist2

Статус: план будущих работ, не отчёт о выполнении. Основания: [аудит dist](audit-dist.md), [аудит dist2](audit-dist2.md), [исследование сервера](server-research.md), [матрица покрытия](COVERAGE.md). Стабильные ID ниже связаны с [опубликованными GitHub Issues](issues/README.md); cutover выполнен и проверен чтением. GitHub Issues — единственный активный источник задач; этот документ — спецификация, не вторая очередь. Никаких реализаций, правок стратегии и серверных экспериментов в рамках подготовки этого плана не выполнено.

## Общий контракт выполнения

Работать только на отдельной одноразовой инсталляции с пустой БД, собственными процессами/сокетами/портами и тестовым пользователем. Перед каждым запуском получить исключительное владение scheduler с fencing, убедиться в идентичности среды и отсутствии других пользователей; истечение lease само по себе не разрешает takeover. Отказ при сомнительной идентичности, занятости или недоступном fence. Setup журналирует каждый созданный ресурс с run/scenario ID; finally восстанавливает глобальные настройки, удаляет только свои объекты и пользователя, проверяет снимок и завершение процессов. Незавершённый cleanup или неизвестный исход команды — quarantine среды и ненулевой итог. Не переносить секреты и живую БД.

**Admission:** SRV должен экспериментально доказать ровно один полный шаг, quiescence релевантных писателей и полей и согласованный снимок DB/Memory относительно откалиброванного Game.time, включая задержки и отказы. `pause`, `roomsDone`, polling или одинаковое время вокруг чтений сами по себе не доказательство. Если этого достичь нельзя, HAR и все per-tick e2e остаются BLOCKED; документ с неизвестными не разблокирует их. API-level проверки могут выполняться отдельно и не называться e2e.

Каждый сценарий использует стартовый снимок S(T), один разрешённый шаг и fence F(T→T+1), затем согласованный снимок S(T+1); повторить для каждого тика до выполнения постусловия или бюджета. Связь Game.time, commit, Memory и intent установить в SRV, не предполагать синхронность. Каждая запись содержит run/scenario/seed, время и фазу, все релевантные объекты с id/type/owner/room/координатами/body/hits/store/capacity/спавном, source, controller, site/progress, drop/decay, Memory и очередь, actionLog/intents с происхождением и фазой, ошибки, CPU и hashes загруженного кода. Пропущенный/двойной тик, недоступное поле, нарушение fence или несогласованный снимок — инфраструктурный FAIL/UNKNOWN, не ноль и не PASS. Хранить весь ряд, а не только начальный и конечный кадр; связать происхождение крипа, приказа, объекта, исполнителя и изменение конкретного target ID. `OK`, actionLog, отсутствие errors и spawn — лишь свидетельства намерения, не результат.

Балансы проверять по дельтам на одном fence: отдельно известные engine generation спавна, стоимость spawn/action, source regeneration, decay, смерть и конкурентные intents. При неизвестной величине сначала калибровать, иначе UNKNOWN. Контроль без исполнителя позволяет отделить регенерацию. Реальные production-модули и engine объекты обязательны; отдельный test entrypoint может вызывать их публичные методы на настоящих объектах, но не переписывать production, не заменять Game/эффекты движка, не вносить в Memory или DB проверяемый результат. Вспомогательный entrypoint и данные fixture отделены от неизменённых модулей; хеши каждого загруженного файла сравниваются с исходником. Непатченный raw main обязательно запускается отдельно от изолированных API тестов.

Параметры бюджета: `R10(T)` и `R100(T)` — число шагов до следующего кратного 10/100 тика с учётом откалиброванной фазы, `Bspawn(body)`, `Bmove(route)`, `Baction`, `Bpath`, `Breload` — экспериментально установленные верхние границы с обоснованием и сохранёнными значениями. Для повторяющихся действий суммировать все итерации: `Nbuild = ceil(remainingProgress/(activeWORK × BUILD_POWER))` по подтверждённым engine constants, с поправкой на доступную энергию и фактически активные части; `Bconstruction = Σ(Bspawn(body_i)+R10_i) + Bpath + Σ Bmove(route_j) + Σ Baction_j + Nbuild×Baction + Σ R100_k + Bupstream`. Здесь i включает все нужные роли, j — все рейсы пополнения, k — все требуемые reconcile; Bupstream включает ожидания очередей, регенерации и подготовки источника. Проверить, что суммарный реальный supply покрывает расход, и пересчитать бюджет при изменении состояния. Это верхняя граница сценария, а не утверждение о числе тиков движка. Исторические 20/30/40 тиков и наблюдения в README не являются гарантиями. Каждый игровой бюджет сопровождается отдельным wall timeout `Wcase`, а операции и дочерние процессы — собственными deadline; зависание, отсутствие прогресса или потеря наблюдения не маскируются. Retry infrastructure допустим только с новым run ID, записью первой ошибки и без автоматического скрытия флаков.

Фикстура F0: принадлежащая контроллеру RCL2 открытая комната, controller (25,25), spawn (10,10), source S1 (15,10), S2 (15,20); свободные клетки, зарезервированные объекты без конкурентов, Memory `{}`, spawn energy 300/300, source capacity/energy и terrain фиксируются фактически. До запуска engine-проверка допустимости fixture обязательна: RCL и ownership, terrain и overlap, проходимый маршрут, capacity/store, допустимость body и активных частей, spawning и достаточный TTL. Некорректный fixture — BLOCKED/infra failure, не дефект стратегии; отдельный намеренно невозможный fixture проверяет этот отказ. Координаты — целевые: если выбранная отдельная комната не позволяет их установить, эквивалентные реальные координаты и проверенные расстояния сохраняются в fixture; неподдерживаемая фикстура BLOCKED. Дополнительные container (16,10), pile (16,11), extension (11,10), site (12,10), повреждённая допустимая структура (13,10), storage flag (20,20) создаются только если сценарий указывает их как вход. Начальный body, store и Memory в каждом варианте являются входом; создаваемый в результате объект/заказ/state не подставляется. Отдельный сценарий изоляции роли вправе начать с site, но не выдавать его за результат строительства.

Результаты: PASS требует всех assertion и cleanup; FAIL — наблюдаемое нарушение; BLOCKED — невозможный admission/fixture; UNKNOWN — потеря доказательства. Известное нарушение получает отдельную запись defect ID с точным воспроизведением и ожидаемым контрактом, его фактический результат RED. Задача реализации тестов может быть завершена, когда oracle и контроли доказаны, воспроизводимый RED стратегии записан в отдельный defect report, а остальные критерии задачи выполнены; исправление стратегии не входит в эти задачи. Отдельная приёмка здоровья стратегии остаётся красной при открытом known-red или неожиданном FAIL. Никаких blanket xfail/skip; XPASS требует повторной проверки и закрытия defect. Раздельно отображать verified behavior coverage и открытые дефекты.

## Исполняемые сценарии

Все варианты ниже наследуют F0, обязательный пошаговый протокол, отрицательные assertions, отдельные run ID, Wcase и cleanup выше. В «T» указано состояние перед реальным вызовом; между каждым последующим событием есть fence и снимок. Состояния и объекты, введённые фикстурой, никогда не учитываются как продукт действия. Периодические вызовы привязывать к реальному Game.time; результат ошибки и промежуточные кадры сохранять.

**SRV-01 — барьер.** На пустой изолированной установке пользователь с одним owned объектом; test probe пишет счётчик в Memory и меняет известное поле Game-объекта через реальное действие. T: счётчик 0; шаги zero/one/N, после каждого снять DB+Memory и счётчики стадий. Проверить один полный игровой цикл на команду: упорядоченные user queue, room queue, первый commitDbBulk, global processor, второй commitDbBulk и increment; число runtime определяется активными пользователями, число processor — активными комнатами фикстуры, а не константой 1. Проверить отсутствие следующего старта до разрешения и соответствие UI/API; негативно задержать runner/processor/save, потерять событие и запросить pause в каждой фазе. Бюджет N выбран исследованием; отдельный wall deadline; прерывание → quarantine. SRV-02 повторяет с несколькими workers, рестартом, поздним ответом и нагрузкой наблюдателя, документирует порядок и overhead. Отсутствие доказательства блокирует HAR.

**HAR-01 — целостная трасса.** F0, один `[MOVE,CARRY,WORK]` с 0 энергии на (14,10), source S1 известной энергии, простейший неизменённый production harvester с `assignedSource` для dist или `sourceId` для dist2. T снимок, каждый шаг до добычи; сверить ID/owner/позицию/store и source, проверка последовательности снимков и фикстуры. Бюджет Bmove+Baction, Wcase. Контроль без крипа. HAR-02 намеренно вызывает потерю fence, срыв setup, timeout, поздний ответ и сбой teardown в изолированной фикстуре; проверить ненулевой итог, сохранение обеих ошибок, отсутствие ложного PASS и quarantine при неопределённой очистке.

**ORD-01 — dist2 resource.** F0, пустая Memory и реальный resourceManager с зарегистрированными четырьмя production классами. T apply source с annotation и реальным sourceId; следующий вызов с той же annotation и изменённым spec; save, JSON/runtime reload, выборка, delete. Проверить стабильный id, отсутствие дубля, сохранение state при изменении spec, корректные методы после reload и отсутствие после delete. Варианты: unannotated ID, неизвестный тип и повторный apply, лишнее поле, неверный тип, отсутствующее поле/null; сверить тип результата/ошибки и состояние с таблицей ниже; строка ошибки — диагностическое свидетельство, а не обязательный публичный контракт, без обещания поддержки неизвестного типа. Бюджет Breload+Baction, Wcase.

**ORD-02 — disabled/priority.** F0 и созданные API ресурсы; true и строка `true` в независимых запусках как управляющий вход: изменить in-memory spec, проверить отсутствующую запись save, затем false и load старого Memory. Контроль false. На реальных id S1/S2 проверить формулу последних шести hex и offsets, сортировку рядом с фиксированными 40/49/50/51/70/80/1000; невалидный id — отдельный API вход. Бюджет Breload+Baction.

**ORD-03 — dist planners и старые API.** F0, S1 с зафиксированной capacity, соседние стены в отдельном варианте, spawn 300, Memory managers/creepId подготовлена как вход изолированного вызова. Вызвать реальные SourceManager/SourceDesc/CreepPlanner и классы данных: проверить workplaces, needWork/carry, distance, queued/живые WORK, schema/body/cost/efficiency при 0/150/300 и ограничении max; отдельно builder fractional, нулевую distance и availableEnergy. Сравнить результаты с таблицей конкретных oracle ниже; тип и обстоятельства исключения записывать, точный текст считать контрактом только при явно публичной гарантии; не представлять дефект как норму. Baction+Bpath, Wcase.

**ORD-04 — dormant/interfaces.** F0 и явная room/creep Memory с `srcDescs`, `assigned_source`, `dst`, очередью и flags; тестовый entrypoint вызывает `EconomyPlanner`, `SpawnPlanner`, `room.harvestPlanner`, `room.consumptionPlanner`, `room.pathPlanner`, `Manager`, `Consumer`, `Producer`/mixin. Проверить периодические/непериодические тики 100/50, изменения и отсутствие записи economy total как характеристику baseline, а не желаемый успешный результат; фактические ошибки (включая roles.keys), no-op и абстрактные исключения. Начальное состояние и наблюдаемые поля сохранить; никаких обещаний работающего path при пустом stub. В отдельных runtime тех же обоих dist проверить Map.fromObject/toObject/filter, flat пустого и вложенного массива с depth 1/2, появление global result; logger: уровни, invalid level, Memory.loggerState и reload. Сравнить с договором API, ошибки/отклонения фиксировать, не выдавать эти проверки за игровые эффекты. Бюджет R100+R50+Baction, где R50 аналогичен R10; API/interface слой отдельно от e2e.

**SPN-01 — план и выбор.** F0, S1, spawn 300, без других крипов; dist: SourceManager/SpawnManager запрашивают и обрабатывают свои заказы, dist2: SourceController/SpawnController создают заказы. T подтвердить очередь и origin, на каждом fence фиксировать priority, тело/стоимость, расход энергии, spawn.spawning, process/queued и полученный creep ID/body/Memory. Варианты свободный/занятый spawn, энергии 0 и достаточная, два приоритета, имя уже существует; при неуспехе нет фиктивного process и расхода. dist2 отдельно highest с невозможным body и нижний возможный: наблюдать текущую остановку и зафиксировать нежелательное starvation как дефект, не тестировать обход как существующий факт. Бюджет R10+Bspawn(body)+Baction для dist2, Bspawn+Baction для dist; Wcase.

**SPN-02 — переход ownership.** F0 с одним source, запустить реальную очередь из SPN-01, не подставлять активный creep. На каждом тике до и после рождения связать order/queued, spawn, имя, ID и source owner; после рождения сделать runtime reload и проверить сохранение ownership. Нет потери привязки или дубликата; известный риск dist при фильтрации queued — RED при воспроизведении. Бюджет Bspawn+Breload+Baction.

**SPN-03 — восстановление.** F0, dist2 заказ создаётся API, а process — настоящим spawn; затем отдельные варианты удалённый/умерший creep, отсутствующий spawn, входной spawning без process и expiry около T. До/после R10 наблюдать pending/active, имя, expiry, удаление process и Memory.creeps, повторный spawn; негативно не создавать ложный active. Для dist проверить удаление умерших queued и повторную постановку. Бюджет R10+Bspawn+Baction.

**ECO-01 — harvest.** F0, `[WORK,CARRY,MOVE]` в (13,10), пустой store, валидный `assignedSource` dist или `sourceId` dist2; источник заданной energy, без других исполнителей. T→движение→успешная добыча→изменение source/store; dist2 дополнительно полный store→drop с новым ID. Отдельный dist production harvester body `[MOVE,WORK]` без CARRY: после проверки реального body наблюдать source→overflow/drop по предварительно откалиброванной семантике движка; не подменять его CARRY-фикстурой. Сравнить с изолированным `[WORK,CARRY,MOVE]` source→store. Контроли: отсутствующий source, spawning, пустой source, без крипа. Бюджет Bmove+Baction; проверять регенерацию отдельно.

**ECO-02 — доставка.** F0, `[CARRY,CARRY,MOVE]` с 0/100 energy, pile 100 в (16,11), spawn и extension с известной свободной capacity; единственный исполнитель. Dist2 задать collect/deliver templates, dist — реальный DeliveryManager и маршруты src→spawn/storage/controller. T проверить источник/потребность/очередь, затем сбор, store, destination, перемещение и передачу или drop, очистку pending и следующий state по каждому fence. Варианты entity/area ground/structure/creep dist2; wait/resource/structure/ground dist; две цели и приоритет, удалённый/полный target, пустой источник, смерть mule, нет маршрута. Контроль без mule и сверка decay/generation: падение его store и рост именно target должны совпадать с учётом калибровки. Проверить pending ровно один раз; dist double subtraction — отдельный RED. Бюджет сумма Bmove+Baction по каждой фазе.

**ECO-03 — upgrader.** F0, `[WORK,CARRY,MOVE]`, 0 энергии, pile 50 около controller и отдельно container 50 в допустимом радиусе (container только dist2), никакого другого крипа. Наблюдать state, pickup/withdraw, заполнение, движение, уменьшение store и рост controller.progress; отрицательные варианты нет энергии/контроллера, spawning, оба источника одновременно. У dist исходник имеет ранний return без pile; различие сохранять. Бюджет Bmove+Baction.

**BLD-01 — patterns.** F0 с реальным terrain и явными стеной/swamp, открытым краем и препятствиями; отдельный production entrypoint вызывает dist2 registry экземпляры single/checkboard/line/ring/rectangle/parallelLines/path/patternPlacer с известными startPos, индексами 0 и за концом, размерами 3 и width 1/2, targetPos у spawn. Наблюдать вывод и CPU, сверить границы, стены, геометрию и отсутствие повторов согласно заявленному контракту, отдельно direction/filled, недоступную комнату и неизвестное имя. Сравнить путь с допустимостью и фактической версией движка, не требовать заранее выдуманный маршрут. Terrain string/object и вложенные opts — отдельные варианты; исторические несоответствия RED. Бюджет Bpath, Wcase.

**BLD-02 — полный construction.** F0, пустая строительная площадка, отсутствуют sites/roads/extensions, builder и энергия появляются через реальную стратегию; raw main либо отдельный реальный BuildController и его order. На T очередь→positions→site ID/owner/тип/координата (не более пяти)→рост progress→исчезновение site и реальная структура→claim ID, каждый fence, затем очередной reconcile без дубля. Никаких вручную подготовленных результатов. Dist2 экспорт/вызов patterns и terrain/opts — исторически известные RED; последующие стадии при пустых positions BLOCKED, не PASS. Dist ConstructionManager вызывать отдельно: RCL1/2, пустые/существующие sites, позиция, deadline на потенциальный цикл; не обещать достижимость через main. Бюджет Bconstruction, включая начальный и повторный R100, все spawn, полные рейсы и Nbuild, Wcase.

**BLD-03 — builder/repair и retry.** Ролевой вход: F0, site (12,10) с допустимым типом и известным progress как вход, `[WORK,CARRY,MOVE]` пустой рядом; заранее проверить engine progressTotal и BUILD_POWER, обеспечить достаточную доступную энергию несколькими реальными рейсами, а не считать pile 50 достаточной для полной дороги; каждый fence собрать, перейти state, построить и увидеть progress/structure и расход энергии. Dist repairer: допустимая на данном RCL структура с фактически проверенными hitsMax и hits=1000, тот же body и энергия; проверить рост hits и расход; отдельные пороговые hitsMax−1000 и 300000 только на типе структуры, чей реальный hitsMax допускает такую фикстуру; иначе использовать пригодный RCL/тип и записать его, чужой/отсутствующий target, отсутствующая энергия. Для dist2 order отдельно исходная совместимая/несовместимая структура, RCL/site-limit, ошибка create, повтор после снятия препятствия, смена count/type/позиции и claim/validate/remove: фиксировать реальные return codes и отсутствие уничтожения чужих объектов. Готовая дорога допускается только как вход repair/claim, не как результат BLD-02. Бюджет Bconstruction для завершения, включая Nbuild и все рейсы. Для repair отдельно Bmove+Nrepair×Baction+все рейсы, где Nrepair вычислен по минимальной проверяемой дельте hits и подтверждённой мощности repair, не по полному восстановлению.

**INT-01 — raw main.** F0 с storage flag для dist, без крипов и подготовленных заказов; загрузить все исходные модули с проверкой hash, выполнить неизменённый main. Каждый тик до порядка manager/controller, очередей, рождения, добычи, доставки и controller progress, а также стройки dist2; ID и причинные балансы обязательны. Missing storage flag, чужая комната без spawn и неполная Memory — независимые негативные варианты. Нет автоматического builder заказа в dist; не обещать стройку через его main. Известные ошибки/пустые positions — RED, отсутствие ошибки и сам spawn не удовлетворяют сценарию. Бюджет Bconstruction с суммой spawn всех необходимых ролей, их R10, рейсами supply и ожиданиями upstream; для отдельных стадий фиксировать собственные дедлайны, Wcase.

**INT-02 — сериализация и restart.** Из INT-01 после реально полученного состояния и отдельно во время spawn сохранить S(T), сбросить только runtime/module cache, не Memory и DB, затем следить Breload+R100+R10+Baction за восстановлением prototypes/routes/costMatrix, state, ownership и отсутствием дубликатов. Отдельно пустая Memory и неконсистентная Memory как вход. Сравнить конкретные ID и spec/state до/после; не править данные ради восстановления.

**GATE-01 — ложные доказательства.** В отдельных F0 контролях без mule дать spawn регенерировать, без builder создать только site как вход, без source-передачи создать creep; запуск acceptance assertions должен отвергнуть delivery/build/harvest. Подставить пропуск тика, неверный owner/origin и устаревший snapshot на уровне теста harness, не production; отчёт должен FAIL/UNKNOWN. Baction, Wcase.

**GATE-02 — полнота и восстановление.** По всем IDs матрицы собрать evidence, hashes, trace и результат cleanup; искусственно вызвать timeout и crash после частичного setup, повторить идемпотентный recovery и проверить quarantine при неизвестном владельце. Нет зелёного результата при RED/BLOCKED/UNKNOWN или неучтённом модуле; отдельный defect report допускает фиксацию baseline без подмены acceptance. Wcase и границы шагов инфраструктурных проверок заданы HAR/SRV.

## Конкретные oracle для граничных случаев

Численные проверки выполняются при подтверждённых engine constants и допустимой фикстуре; недопустимые body проверяются как отрицательный engine-вход и не превращаются в фиктивный spawn. Для gameplay использовать реальные серверные ID; искусственные hex-строки допустимы только в изолированном вызове priority helper.

| Вход | Ожидание и разделение baseline/контракта |
|---|---|
| dist2 priority `000001`, offset 0 / 10 | Число 100 / 90; `000002`, 0 → 200. Невалидная hex-строка: наблюдать `NaN` как характеризацию, не выдавать её за допустимый игровой priority. |
| Resource с допустимым string id и annotation, затем повторный apply той же annotation | Один ID, изменение только указанного spec, сохранение state; после сериализации и reload экземпляр имеет методы класса. |
| Неизвестное поле или неверный тип schema | Конструктор отклоняет вход ошибкой; Отсутствующее поле и null в скалярном поле характеризуются как допускаемые исходником, без объявления их желательными для обязательного игрового ресурса; null во вложенном metadata вызывает TypeError при Object.keys(null), что является характеристикой baseline, а не желаемой семантикой ошибки. Неизвестный тип и повторный apply: зафиксировать ошибку/состояние без ложной гарантии поддержки. |
| CreepOrder: budget ниже цены constant; ровно цена constant; выше на цену ratio-набора | Соответственно `null`, constant body, constant плюс один целый ratio-набор при разрешённом maxCost; проверять цену по engine BODYPART_COST и отсутствие нецелого набора. |
| body из 0 частей, допустимый минимальный, 50 частей и 51+ частей | Проверить вычисленный массив отдельно от решения настоящего spawnCreep. Engine rejection 0/51+ не создаёт spawnProcess, не расходует энергию и не переводит order в spawning; 50 частей принимать только при допустимых body/cost/энергии и версиях engine. Отсутствие явного cap у dist2 — риск, не требование принять 51. |
| dist planner с бюджетом 0 и body minimum | Бюджет 0 возвращает отсутствие допустимого тела; при достаточном бюджете проверить выданные части и сумму BODYPART_COST. Fractional builder проверяется отдельно с типом фактической ошибки; не считать исключение желаемым. |
| SourceDesc/SourceManager, S1 с capacity 3000 и зафиксированным terrain | Проверить число фактически свободных соседних клеток; dist needWork = 5 при этой capacity; сравнить с отдельным вариантом занятого terrain и реальным числом активных WORK. Distance/carry вычислять по зафиксированному маршруту; нулевая distance — отдельный негативный случай. |

Стоимость и скорость движения оценивать независимо по фактически активным частям, массе и fatigue, с проверкой engine constants; не считать геометрическое расстояние числом тиков без калибровки.

**INT-03 — dispatch и изоляция ошибок dist2.** F0: одновременно один spawning creep, один creep с неизвестной ролью, один реальный mule с отсутствующими шаблонами (или upgrader без controller в отдельной допустимой комнате, если это вызывает реальную ошибку), и второй валидный harvester `[WORK,CARRY,MOVE]` у S1. Настроить порядок имён так, чтобы ошибочный выполнялся раньше валидного; не менять production роль. На каждом fence записать лог warning/error, Memory и DB: spawning и unknown не действуют, ошибка конкретной роли перехвачена dispatcher, следующий валидный creep действительно добывает, а не только получает intent. Изолированно проверить `roles.exists` для известных/неизвестных имён и точный набор `getAll`. Если engine не разрешает fixture без controller, использовать mule-вариант; невозможность вызвать ошибку — BLOCKED, не симулировать исключение. Бюджет Bmove+Baction, Wcase и общий cleanup.

**BLD-04 — выбор и потеря target.** В отдельной допустимой F0 два собственных sites с разными расстояниями и созданными через реальный resourceManager заказами разных priority; builder `[WORK,CARRY,MOVE]` с достаточной энергией. Снимать оба site ID/progress и targetSiteId на каждом fence: проверить желаемый выбор высокого priority; при отсутствии заполненной `constructionSites` карты зафиксировать фактический выбор по расстоянию как RED, не нормативный успех. Удалить выбранный site контролируемым событием, следующий fence должен показать очистку устаревшего ID и выбор оставшегося; вариант без сайтов возвращает idle. Бюджет Bmove+Baction на каждую фазу, отдельный Wcase и cleanup.
