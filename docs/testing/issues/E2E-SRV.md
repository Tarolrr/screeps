# E2E-SRV: Исследовать изолированный сервер, пошаговый запуск и согласованные снимки

Подробное ТЗ подготовлено по аудиту всех собственных production-модулей dist и dist2 и прошло независимое ревью. Постановка: #4. Пользователь поручил после подготовки задач занять агентов их выполнением.

## Результат и приёмка

Исследование версии движка, одноразовой установки, scheduler и coherent snapshot; зависимостей нет.

Воспроизводимые probes SRV-01/02, протокол запуска, идентификация версий/путей без секретов, доказанный fence/step, отчёт о задержках, отказах, CPU overhead и recovery. Если доказательство не удалось — явный BLOCKED, а не выдача документа за admission.

## Обязательный протокол каждого сценария

Работать только на отдельной одноразовой инсталляции с пустой БД, собственными процессами/сокетами/портами и тестовым пользователем. Перед каждым запуском получить исключительное владение scheduler с fencing, убедиться в идентичности среды и отсутствии других пользователей; истечение lease само по себе не разрешает takeover. Отказ при сомнительной идентичности, занятости или недоступном fence. Setup журналирует каждый созданный ресурс с run/scenario ID; finally восстанавливает глобальные настройки, удаляет только свои объекты и пользователя, проверяет снимок и завершение процессов. Незавершённый cleanup или неизвестный исход команды — quarantine среды и ненулевой итог. Не переносить секреты и живую БД.

**Admission:** SRV должен экспериментально доказать ровно один полный шаг, quiescence релевантных писателей и полей и согласованный снимок DB/Memory относительно откалиброванного Game.time, включая задержки и отказы. `pause`, `roomsDone`, polling или одинаковое время вокруг чтений сами по себе не доказательство. Если этого достичь нельзя, HAR и все per-tick e2e остаются BLOCKED; документ с неизвестными не разблокирует их. API-level проверки могут выполняться отдельно и не называться e2e.

Каждый сценарий использует стартовый снимок S(T), один разрешённый шаг и fence F(T→T+1), затем согласованный снимок S(T+1); повторить для каждого тика до выполнения постусловия или бюджета. Связь Game.time, commit, Memory и intent установить в SRV, не предполагать синхронность. Каждая запись содержит run/scenario/seed, время и фазу, все релевантные объекты с id/type/owner/room/координатами/body/hits/store/capacity/спавном, source, controller, site/progress, drop/decay, Memory и очередь, actionLog/intents с происхождением и фазой, ошибки, CPU и hashes загруженного кода. Пропущенный/двойной тик, недоступное поле, нарушение fence или несогласованный снимок — инфраструктурный FAIL/UNKNOWN, не ноль и не PASS. Хранить весь ряд, а не только начальный и конечный кадр; связать происхождение крипа, приказа, объекта, исполнителя и изменение конкретного target ID. `OK`, actionLog, отсутствие errors и spawn — лишь свидетельства намерения, не результат.

Балансы проверять по дельтам на одном fence: отдельно известные engine generation спавна, стоимость spawn/action, source regeneration, decay, смерть и конкурентные intents. При неизвестной величине сначала калибровать, иначе UNKNOWN. Контроль без исполнителя позволяет отделить регенерацию. Реальные production-модули и engine объекты обязательны; отдельный test entrypoint может вызывать их публичные методы на настоящих объектах, но не переписывать production, не заменять Game/эффекты движка, не вносить в Memory или DB проверяемый результат. Вспомогательный entrypoint и данные fixture отделены от неизменённых модулей; хеши каждого загруженного файла сравниваются с исходником. Непатченный raw main обязательно запускается отдельно от изолированных API тестов.

Параметры бюджета: `R10(T)` и `R100(T)` — число шагов до следующего кратного 10/100 тика с учётом откалиброванной фазы, `Bspawn(body)`, `Bmove(route)`, `Baction`, `Bpath`, `Breload` — экспериментально установленные верхние границы с обоснованием и сохранёнными значениями. Для повторяющихся действий суммировать все итерации: `Nbuild = ceil(remainingProgress/(activeWORK × BUILD_POWER))` по подтверждённым engine constants, с поправкой на доступную энергию и фактически активные части; `Bconstruction = Σ(Bspawn(body_i)+R10_i) + Bpath + Σ Bmove(route_j) + Σ Baction_j + Nbuild×Baction + Σ R100_k + Bupstream`. Здесь i включает все нужные роли, j — все рейсы пополнения, k — все требуемые reconcile; Bupstream включает ожидания очередей, регенерации и подготовки источника. Проверить, что суммарный реальный supply покрывает расход, и пересчитать бюджет при изменении состояния. Это верхняя граница сценария, а не утверждение о числе тиков движка. Исторические 20/30/40 тиков и наблюдения в README не являются гарантиями. Каждый игровой бюджет сопровождается отдельным wall timeout `Wcase`, а операции и дочерние процессы — собственными deadline; зависание, отсутствие прогресса или потеря наблюдения не маскируются. Retry infrastructure допустим только с новым run ID, записью первой ошибки и без автоматического скрытия флаков.

Фикстура F0: принадлежащая контроллеру RCL2 открытая комната, controller (25,25), spawn (10,10), source S1 (15,10), S2 (15,20); свободные клетки, зарезервированные объекты без конкурентов, Memory `{}`, spawn energy 300/300, source capacity/energy и terrain фиксируются фактически. До запуска engine-проверка допустимости fixture обязательна: RCL и ownership, terrain и overlap, проходимый маршрут, capacity/store, допустимость body и активных частей, spawning и достаточный TTL. Некорректный fixture — BLOCKED/infra failure, не дефект стратегии; отдельный намеренно невозможный fixture проверяет этот отказ. Координаты — целевые: если выбранная отдельная комната не позволяет их установить, эквивалентные реальные координаты и проверенные расстояния сохраняются в fixture; неподдерживаемая фикстура BLOCKED. Дополнительные container (16,10), pile (16,11), extension (11,10), site (12,10), повреждённая допустимая структура (13,10), storage flag (20,20) создаются только если сценарий указывает их как вход. Начальный body, store и Memory в каждом варианте являются входом; создаваемый в результате объект/заказ/state не подставляется. Отдельный сценарий изоляции роли вправе начать с site, но не выдавать его за результат строительства.

Результаты: PASS требует всех assertion и cleanup; FAIL — наблюдаемое нарушение; BLOCKED — невозможный admission/fixture; UNKNOWN — потеря доказательства. Известное нарушение получает отдельную запись defect ID с точным воспроизведением и ожидаемым контрактом, его фактический результат RED. Задача реализации тестов может быть завершена, когда oracle и контроли доказаны, воспроизводимый RED стратегии записан в отдельный defect report, а остальные критерии задачи выполнены; исправление стратегии не входит в эти задачи. Отдельная приёмка здоровья стратегии остаётся красной при открытом known-red или неожиданном FAIL. Никаких blanket xfail/skip; XPASS требует повторной проверки и закрытия defect. Раздельно отображать verified behavior coverage и открытые дефекты.

## Сценарии

**SRV-01 — барьер.** На пустой изолированной установке пользователь с одним owned объектом; test probe пишет счётчик в Memory и меняет известное поле Game-объекта через реальное действие. T: счётчик 0; шаги zero/one/N, после каждого снять DB+Memory и счётчики стадий. Проверить один полный игровой цикл на команду: упорядоченные user queue, room queue, первый commitDbBulk, global processor, второй commitDbBulk и increment; число runtime определяется активными пользователями, число processor — активными комнатами фикстуры, а не константой 1. Проверить отсутствие следующего старта до разрешения и соответствие UI/API; негативно задержать runner/processor/save, потерять событие и запросить pause в каждой фазе. Бюджет N выбран исследованием; отдельный wall deadline; прерывание → quarantine. SRV-02 повторяет с несколькими workers, рестартом, поздним ответом и нагрузкой наблюдателя, документирует порядок и overhead. Отсутствие доказательства блокирует HAR.

Пути ниже относятся к установленным пакетам `~/screeps/node_modules/@screeps/`; номера строк относятся к текущей установке, при обновлении нужны повторная проверка и фиксация версий/хешей.

Это не реализация доказанного барьера или однотикового шага. Здесь нет `step`.

## Среда и разрешения

Нужна отдельная одноразовая инсталляция с новой пустой БД, собственными рабочим каталогом, storage socket, CLI и HTTP/WebSocket портами, логами и тестовыми пользователями. Указать точные версии Node, пакетов, lockfile, ОС и ABI нативных зависимостей; проверить сборку/загрузку под выбранным Node, не предполагать переносимость `node_modules`. Создать конфигурацию без реальных ключей; не клонировать общий мир, пользователей, токены, `.screepsrc` или живую БД. Проверить фактические пути и отсутствие совпадения с действующим сервером до старта. Комната в общем мире не изолирует глобальные тики, scheduler и настройки: без исключительного владения scheduler она недостаточна.

Каждый прогон получает ownership lease на всю выделенную инсталляцию, с идентификатором владельца/запуска, проверкой процесса и fencing от конкурентного контроллера; истечение времени само по себе не разрешает takeover. Протокол аварийного восстановления должен проверять владельца и состояние процессов. Использовать минимальные права, локальные сокеты, ограниченный срок и отдельный каталог артефактов; не сохранять секреты и чужой код. После отказа оставить диагностические артефакты и безопасно уничтожить только помеченную одноразовую среду. Любая операция на другом сервере запрещена.

## Исследовательский протокол и калибровка

Предположение для проверки: возможно организовать границу между завершением одного полного цикла и началом следующего через hooks/управляемый scheduler или расширение сервера. Ни polling, ни `pauseSimulation`, ни `roomsDone` пока не объявляются таким барьером. Сначала проверить фактически загружаемые исходники, версии, моды, очереди, физические и логические границы commit/save, задержанные записи, порядок custom stage и работу фоновых cron/worker. Определить, какая именно фаза означает «тик T завершён» и как ей соответствует `Game.time`, env `gameTime`, payload события и сохранённая Memory.

На выделенной среде создать исполняемые probes с машинно-проверяемым журналом:

1. Маркеры начала/конца и последовательности для runtime, сохранения Memory/intents, processor, обоих commit, increment, notifications и custom stage; сверить их с gameTime, счётчиком в Memory и изменением объекта. Проверить zero, one и N шагов при разных задержках и нескольких runner/processor, отложенных сохранениях и пустых/активных комнатах.
2. Запросить pause во всех фазах и измерить in-flight работу, очередь, изменения после ответа и после предполагаемой quiescence. Повторные paused reads с искусственно задержанными workers и фоновыми задачами должны выявлять гонки; стабильное время недостаточно. Проверить остановку, ошибки, таймауты, рестарт и потерю события. Документировать точный критерий барьера и наблюдаемые исключения.
3. Проверить candidate bounded step: ровно один полный цикл и ровно одно изменение номера на команду, без следующего старта до подтверждения снимка, включая повтор команды, disconnect и отказ worker. Если штатный API этого не обеспечивает, исследовать тестовый scheduler/hook и его границы; до реализации и калибровки сценарии с per-tick гарантией блокируются, а не понижаются до polling.
4. Проверить атомарность снимка DB/env/Memory: версии или маркеры до/после, параллельные записи, чтения на паузе, фоновые операции и согласование с UI/API. При отсутствии атомарного чтения доказать quiescence всех писателей либо реализовать явный барьер/снимок; смешанный снимок должен считаться ошибкой инфраструктуры. Проверить eventLog/history/intents на доступность, время жизни и потери; подписка pubsub сама не является надёжным журналом.
5. Калибровать нагрузку наблюдателя: сравнить одинаковые прогоны без него и с ним, длительность, CPU и влияние на порядок; установить бюджет и проверить стабильность. Зафиксировать результаты, команды, версии, ограничения и воспроизводимые probes в документации по работе с сервером, включая реально обнаруженные недокументированные особенности. Не делать вывод о семантике по одному удачному прогону.

## Контракт будущего снимка

Для каждого проверенного перехода сохранять tick start/end, идентификатор фазы и источник времени, монотонную последовательность событий и проверку отсутствия пропущенных/двойных тиков; несогласованность, пробел или неизвестная фаза — infrastructure failure. Связать входное состояние T, исполнение стратегии и результаты обработки с соответствующим конечным состоянием по откалиброванной семантике. Записывать выбранные поля объектов с `_id`, типом, комнатой, координатами, владельцем, телом/hits, store/capacity, временем жизни/decay и релевантными полями; источники, контроллер, спавны и структуры, construction sites/progress, drops, tombstones. Сопоставлять появление, исчезновение, замену и превращение site→structure по идентичности и координатам, не считать разные ID одним объектом.

Собирать Memory пользователя и нужные segments, CPU/bucket и сведения об исполнении/ошибках скриптов; actionLog, доступные intents и event trace подписывать фазой и происхождением. Намерение, `OK` и запись actionLog не доказывают эффект: сверять изменения состояния и балансы ресурсов, progress/hits, учитывая расход, генерацию спавна, регенерацию источника, decay, смерть и внешние эффекты. При недоступности поля отмечать unknown, а не ноль или PASS. Схема и её версия, версии сервера и стратегия с хешами загруженных модулей обязательны; drift схемы должен явно ломать проверку или иметь версионированный адаптер.

На сбой сохранять run/scenario/replay IDs, seed и параметры генерации, версии/хеши зависимостей и кода, конфигурацию без секретов, границы времени и фаз, исходную фикстуру, трассу и снимки до/после, логи инфраструктуры, причину отказа и метрики overhead. Replay должен явно указывать источники недетерминизма и не обещать идентичность без проверки.

## Риски существующей обвязки и требования

`runCase` принимает `timeoutMs`, но не применяет его; `run-all.js` вызывает `spawnSync` без timeout. Зависание дочернего процесса может остановить suite. CLI timeout не отменяет серверный eval, сокетные ошибки/закрытие и поздний ответ требуют явной обработки и изоляции команд. Нужны ограниченные deadlines на весь процесс и операции, отмена/kill с проверкой исхода, ненулевой exit при ошибке, сигнале, timeout, неизвестном результате или ошибке cleanup. PASS печатается до teardown; teardown способен упасть после него. Итог должен зависеть от теста и cleanup, с сохранением обеих ошибок.

Setup меняет мир последовательно; сбой до присвоения `ctx.userId`, обрыв сокета или процесс могут оставить частичные данные. `destroyUser` восстанавливает контроллер лишь частично, удаляет новые нейтральные объекты по baseline и не является транзакционным откатом; возможны гонки, потери чужих объектов, пропущенные данные и незавершённый cleanup. В `test4` `p1.x` читается до проверки `p1`; cleanup первого пользователя при ошибке может не дойти до второго. Требуются журнал ресурсов, идемпотентное восстановление и проверка результата на выделенной установке, а при неопределённости — quarantine среды.

Критерии также допускают ложные выводы: test1 вычисляет CPU delta, но не проверяет её; test2 порог spawn ≥50 не ограничен 50 тиками и может достигаться регенерацией; test4 считает отсутствие цели повреждением/уничтожением без доказательства причины; test5 может пропустить короткоживущий site; test6/7 проверяют только появление крипа и notifications, не корректность стратегии. Deep xfail читает ошибки в teardown, но не проверяет их как условие теста; чтение с `.catch(() => [])` скрывает сбой диагностики. Нужны явные предусловия, ограниченные тики, причинные проверки и различение failure/unknown/xfail. Эти проблемы здесь не исправляются.

## Отдельные задачи

**1. Исследовать сервер и документировать.** Предусловия: выделенная установка, lease и права локального администратора только на неё. Провести перечисленные probes, установить границы и гонки, проверить возможный bounded step и coherent snapshot; зафиксировать команды, исходники/версии, результаты, ограничения, безопасные процедуры запуска, восстановления и очистки. DoD: воспроизводимая документация-протокол и исполняемая калибровка с позитивными и намеренно сломанными случаями; каждый неподтверждённый механизм отмечен неизвестным, принято решение о необходимости тестового hook. При невозможности доказать барьер задача сообщает блокировку, а не утверждает поддержку.

**2. Реализовать harness, fixtures и observer.** Предусловия: результаты задачи 1 и проверенный контракт фаз/изоляции. Реализовать управление жизненным циклом одноразового мира и lease, проверяемую подготовку фикстур, ограниченный scheduler, согласованные снимки и трассу по контракту выше, диагностику, deadlines, корректные статусы и аварийную очистку. Acceptance: калибровка доказывает ровно N последовательных переходов, отсутствие потерь/дублей и согласованность данных; инъекции задержек, исключений, потери связи, зависания и сбоя cleanup дают явный failure с артефактами и без выхода за выделенную среду. DoD включает тесты инфраструктуры, версионирование схемы и руководство запуска/replay.

Scenario suite зависит от этих задач: smoke polling может оставаться явно помеченным ограниченным наблюдением, но модульные причинные проверки каждого тика и UI-подобная история допускаются только после калибровки. Фикстуры должны давать начальные условия и проверять эффекты независимо для отдельных модулей и интеграционных цепочек; известный xfail не превращать в PASS без выполнения его фактических критериев.

## Границы работы

- Исполнение делегировано агентам под lease координатора; только координатор меняет Issues и метки.
- Стратегию dist/dist2 не исправлять ради зелёных тестов. Дефект кода оформлять отдельно с трассой; приёмка реализации теста и здоровье стратегии различаются.
- Не изменять работающий пользовательский сервер. Все эксперименты — в выделенной одноразовой установке.
- Не включать scheduler, не публиковать секреты, не выполнять push или merge.
- Каноническое ТЗ в рабочем репозитории: docs/testing/PLAN.md, COVERAGE.md и аудиты. Этот файл — текст issue, не отдельная очередь.
