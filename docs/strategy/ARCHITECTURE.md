# Архитектура приложения стратегии Screeps

Статус: **спецификация будущей реализации**, задача [#17](https://github.com/Tarolrr/screeps/issues/17), 2026-11-08. Основание — стратегия [DESIGN](DESIGN.md) после [критического ревью](critical-review-2026-11-08.md). Здесь заданы технические границы, жизненный цикл данных и действий. Стратегические приоритеты, пороги и критерии выгодности остаются в DESIGN; приложение реализует их без собственного второго набора правил.

В комплект входят [интеграция с dist2](INTEGRATION.md) и [ограничения runtime](RUNTIME-CONSTRAINTS.md). Код стратегии этой задачей не реализован. При конфликте описания текущего dist2 с предлагаемыми интерфейсами следует сначала читать раздел «фактическое поведение» в INTEGRATION; новые методы ниже ещё предстоит создать.

## 1. Технические решения и границы

Один синхронный процесс на игровой tick, один composition root и явный конвейер. Без фоновых потоков, сетевых сервисов, общей шины с неупорядоченными подписчиками и скрытого service locator. Язык первой реализации — JavaScript CommonJS с JSDoc-типами; смена языка не требуется для этапа A.

Предлагаемое дерево исходников:

```text
src/bot/
  main.js                      composition root, единственный export loop
  app/                         TickRunner, OwnershipRouter, FaultBoundary, WorkBudget
  state/                       StateStore, StateCodec, MigrationRegistry
  observation/                 ScreepsReader, WorldSnapshotBuilder, EffectMatcher
  domain/                      DTO, ключи, состояния, инварианты, reason codes
  models/                      EconomyModel, ThreatModel, ForecastCalendar
  planning/                    RoomGovernor, EmpirePlanner, MissionPlanner
  scheduling/                  BudgetLedger, SpawnScheduler, AssignmentScheduler
  execution/                   IntentArbiter, IntentGateway, SafetyKernel, executors
  integration/                 LegacyAdapter, HandoverCoordinator, ImportProjection
  telemetry/                   DecisionRecorder, MetricsAggregator, ReplayExporter
```

Это логические пакеты; нет требования создать класс на каждый DTO. Простые вычисления оформляются функциями. `domain`, `models`, `planning` и расчётная часть `scheduling` не импортируют Game, Memory, singleton legacy или сетевой клиент. Они получают значения и возвращают значения. `app` связывает экземпляры явными параметрами; зависимости создаются один раз после reset, но корректность не зависит от сохранения heap.

Выбор слоёв сохраняет возможность использовать существующие роли как временные адаптеры и проверять модели без движка. ECS и полная переработка населения не требуются для первых этапов; распределённые сервисы добавили бы несвойственную одному loop координацию. Полное event sourcing также не выбрано: наблюдения игры неполны, поэтому журнал намерений и снимки не объявляются полной историей мира. Эти альтернативы можно пересмотреть после измерений, без изменения публичных DTO моделей.

Runtime-адаптер читает Game/Memory. StateStore единолично изменяет новое долговременное состояние. Gateway единолично вызывает изменяющие игровой мир методы. LegacyAdapter — временное исключение для старых исполнителей: он обязан обеспечить те же проверки владения и запреты конфликтов, прежде чем режим adaptive будет разрешён. Прямые вызовы Game из существующих ролей нельзя объявить изолированными одним интерфейсом поверх main.

Сборка: будущий esbuild bundle CommonJS в `build/strategy/main.js`, загрузка как Screeps-модуль `main`; bare imports legacy разрешаются явными aliases. В артефакте нет runtime-зависимости от Node filesystem или npm. Не импортировать `dist2/main.js`, потому что при загрузке он создаёт ресурсы. Все top-level новых модулей объявляют код/константы, не создавая заказы и не записывая Memory. До внедрения проверить целевым загрузчиком артефакт, экспорт loop и reset. Подробности поставки — в INTEGRATION.

## 2. Владение данными и действиями

| Данные/ресурс | Авторитетный источник | Единственный writer/распорядитель |
| --- | --- | --- |
| Текущее положение, store, hits, body, spawning | Game текущего тика | Игровой движок; приложение только наблюдает |
| Режим, эпоха, переход комнаты | StateStore → OwnershipRouter | Router через StateStore |
| Миссии, потребности, задания, история | Memory.strategy | StateStore принимает проверенные patches |
| Резервы и обещания | Датированный ledger + текущий снимок | BudgetLedger через StateStore |
| Порядок spawn | Подтверждённые потребности, живые/spawning связи | SpawnScheduler |
| Назначение крипа | Домашний домен и sidecar binding | AssignmentScheduler |
| Реальные intents | Принятый пакет + право владения | IntentGateway; legacy только через ограждённый адаптер |
| Глобальный safe mode/межкомнатная помощь | Снимки всех комнат и DESIGN | Empire coordinator; комнаты формируют запросы |
| Теневые прогнозы | Те же DTO, отдельное состояние | ShadowStore в Memory.strategyShadow |

Домен крипа — стабильная домашняя комната из binding, не текущая комната. Структуры принадлежат своему комнатному домену; нейтральный remote назначается одному дому. План передачи энергии резервирует источник и ёмкость получателя, не даёт двум задачам право на один груз. Между legacy/adaptive доменами в v1 нет хозяйственных миссий до миграции обоих концов. Перед каждым изменением проверяется токен `{room, owner, epoch}` и разрешённая фаза перехода. Токен не является серверной блокировкой: он обеспечивает дисциплину единственного маршрутизатора кода.

Снимок на tick T неизменяем. OBSERVE создаёт критический срез, фаза FORECAST добавляет только ещё не снятые поля в полный Snapshot той же эпохи наблюдения; уже снятые значения не переписываются результатами intents. Предложения несут fingerprint использованных полей, поэтому добавление независимого поля само по себе не делает их устаревшими. Результат планирования виден нижележащим фазам только после принятия пакета в контекст T; это **изменение плана**, а не изменение снимка мира. Принятый transfer не увеличивает наблюдаемый store в этом же тике. Нижележащая фаза видит и Snapshot, и IntentReservations, поэтому не обещает ту же энергию повторно.

## 3. Фазы одного тика

| Фаза | Работа | Разрешённые изменения и результат |
| --- | --- | --- |
| 0. BOOT | Проверить build/schema, загрузить state, определить владельцев и незаконченные переходы | Только StateStore/control; при несовместимости запрет обычного исполнения в затронутом домене |
| 1. OBSERVE | Снять собственные объекты, critical threats, видимость и предыдущие события | DTO снимок T; события имеют observedAt=T и effectTick=T−1 |
| 2. RECONCILE | Сверить команды прошлых тиков, рождения/смерти, bindings, истёкшие назначения | Пакет изменений фактов и статусов; восстановить доступный текущий ledger |
| 3. CRITICAL | Вычислить и выдать срочные защитные/восстановительные действия | Резервировать права действия/ресурсы, записать логическое намерение, вызвать Gateway |
| 4. FORECAST | Достроить полный снимок, потоки, календарь и режимы | Чистые модели; недоступное поле = unknown, не ноль |
| 5. PLAN | Пересмотреть governor/empire/миссии по периодам и событиям DESIGN | Proposals с ожидаемой revision и зависимостями |
| 6. ADMIT | Проверить предложения и выделить бюджет, spawn и задания | Единый принятый пакет; при конфликте отклонить целиком предложение, не половину зависимостей |
| 7. EXECUTE | Превратить принятые задания и продолжающиеся назначения в intents | Проверки владельца/ресурса/конфликтов; Gateway, receipts вызовов |
| 8. CLOSE | Записать ограниченную телеметрию, курсоры и итог фазы | StateStore final checkpoint; не заменяет следующее наблюдение мира |

Фазы 0–3 имеют приоритет CPU. Для этого RECONCILE сначала обрабатывает control, реальные spawn/критические bindings и необходимые им receipts; остальная история может продолжиться в фазе 4. Критическое решение не ждёт полного необязательного прогноза. Уже выданный critical intent занимает actor/actionSlot и необходимые ресурсы до конца T: EXECUTE не заменяет его последующим «более выгодным» предложением.

Нет ожидания следующего тика внутри loop. Многошаговая работа хранит статус и продолжается при следующем вызове. Если нужны дополнительные Game-чтения, их выполняет Reader; новая информация получает field version. Планы с более старой зависимостью заново проверяются перед вызовом Gateway. Случайно сохранившийся кэш не служит фактом.

Legacy и shadow тоже входят в этот конвейер, но имеют иную полосу исполнения: legacy-эффекты выполняются ровно один раз в отведённой EXECUTE-фазе, shadow не получает Gateway. Во время этапа A новая CRITICAL-полоса для shadow выключена: текущим ботом по-прежнему владеет legacy. Новый порядок защитных действий обязателен для adaptive, а не незаметное изменение baseline при включении наблюдения.

Глобальный бюджет резервирует время для критической работы остальных комнат, а не позволяет первой комнате съесть весь tick. Очерёдность: комнаты с наблюдаемой угрозой, затем ожидающие critical deadline, затем стабильный циклический порядок. WorkBudget проверяется перед каждым блоком; лимиты боевого оценщика берутся из DESIGN. Нехватка бюджета откладывает вычисление и сохраняет cursor; незавершённый расчёт не даёт положительного допуска. Полностью исчерпанный CPU может оборвать любой шаг — приложение не обещает невозможного продолжения.

## 4. Интерфейсы и результаты

Все интерфейсы синхронные. Ссылки на DTO read-only; имена ниже служат контрактом первой реализации. Коллекции сортируются по стабильному ключу. Случайность, если понадобится эксперименту, подаётся seed-источником явно.

```text
StateStore.open(rawMemory, buildInfo) -> OpenResult<StateView>
Reader.capture(tick, scope, observationBudget) -> Snapshot
Reconciler.reduce(snapshot, state, pendingOps) -> ReconciliationPatch
EconomyModel.evaluate(snapshot, state, horizon) -> EconomyAssessment
ThreatModel.evaluate(snapshot, intel, budget) -> ThreatAssessment
RoomGovernor.propose(context, roomState) -> Proposal[]
EmpirePlanner.propose(context, roomProposals) -> Proposal[]
MissionPlanner.advance(context, mission) -> MissionPatch + Demand[]
SpawnScheduler.schedule(context, demands, ledgerView) -> SpawnPlan
AssignmentScheduler.assign(context, demands, bindings) -> AssignmentPlan
BudgetLedger.admit(context, proposal, schedules) -> AdmissionResult
IntentArbiter.select(context, commands) -> AcceptedCommand[]
Gateway.issue(command, currentFacts, token) -> CallReceipt
StateStore.apply(expectedRevision, patches) -> ApplyResult
Recorder.append(decisionOrObservation) -> bounded telemetry
```

`context` содержит tick, immutable snapshot, state revision, версии модели/политики, owner tokens, capability flags среды, WorkBudget и принятые ранее резервирования. Он не содержит raw Game или изменяемую Memory. Только Reader/Gateway/StateStore имеют такие порты. Расчёт будущих тел и путей получает константы/terrain DTO либо ограниченный PathService; PathService не выдаёт intents.

Результат вычисления — `READY(value, inputFingerprint)`, `DEFERRED(cursor, reason)` или `UNKNOWN(reason, missingFields)`. Отказ в проекте — `REJECTED(reasonCode, evidence)`, не исключение. Admission возвращает также IDs всех резервирований и expected revision; пакет отвергается, если revision/owner/fingerprint поменялись. Повторное применение одного patchId ничего не создаёт.

Команда содержит `commandId`, `operationKey`, `ownerToken`, `actorRef`, `action`, `targetRef`, `amount/body`, `issuedForTick`, `reservationIds`, `preconditions`, `priority` и `missionId`. `actorRef` — id либо устойчивое имя собственного крипа; позиции всегда `{roomName,x,y}`. Команда допустима только в своём тике. Не выполненная команда переносится как потребность, а не как автоматически повторяемый старый intent.

`CallReceipt` — только `RETURNED(code)` или `THREW(errorCode)` с actor/target/tick, а не подтверждение эффекта. Нельзя выдать деньги на основании возвращённого OK. EffectMatcher отдельно выдаёт `CONFIRMED(effect)` / `NO_EFFECT(evidence)` / `UNKNOWN(reason)`. Внутри предметной области эти два типа не взаимозаменяемы.

Минимальные reason codes: `STALE_OWNER`, `STALE_INPUT`, `NO_VISIBILITY`, `INSUFFICIENT_LIQUIDITY`, `CRITICAL_DEADLINE`, `BUDGET_DEFERRED`, `AMBIGUOUS_EFFECT`, `INCOMPATIBLE_SCHEMA`, `UNSUPPORTED_CAPABILITY`, `LEGACY_BINDING_CONFLICT`. В журнале хранится код и значения, позволившие его проверить; человекочитаемый текст генерируется поверх.

`Proposal` содержит id, room/missionId, inputFingerprint, expectedRevision, reasonCode, demands, необходимые изменения миссии и набор связанных резервирований; ADMIT принимает его как одну единицу. `Demand` из DESIGN дополнен measurementUnit (`energy/tick`, `work/tick`, `coverage`), demandStableKey и generation. `Assignment` содержит id, demandKey/generation, actorName, homeRoom/ownerEpoch, taskType, source/targetRef, amountLimit, reservationIds, routeVersion, deadline и state (`ASSIGNED`, `TRAVELLING`, `WORKING`, `VERIFYING`, `DONE`, `CANCELLED`, `UNKNOWN`). Смена taskType не переносит скрытый transient state старой роли: адаптер строит новый executor context. Состояние DONE устанавливается только по контракту требуемого эффекта; смерть исполнителя сама по себе означает прекращение assignment и отдельную сверку уже выданных операций.

## 5. Ledger, команды и наблюдение эффектов

Внутренняя атомарность означает проверку и принятие одного целого **пакета плана** в синхронной функции. Она не означает ACID между Memory и миром. Перед API StateStore записывает подготовленное намерение и reservation, затем Gateway возвращает CallReceipt; следующий тик устанавливает эффект. CPU termination может оставить любое сочетание старого state и уже выполненного эффекта. Ограничения подробно разобраны в RUNTIME-CONSTRAINTS.

`operationKey = domain / ownerEpoch / demandStableKey / generation / action / occurrence` (эпоха происхождения операции фиксирована). Для spawn имя выводится из этой идентичности, без `Game.time % 2`. Смена generation происходит только после сверки покрытия потребности живыми и spawning исполнителями. `commandId` добавляет issuedForTick; повторная попытка операции использует тот же operationKey и имя до подтверждённого завершения попытки. Имена создаются коротким детерминированным хешем полного ключа; полный ключ хранится в binding, коллизия имени с другим ключом — блокирующий конфликт, а не переиспользование чужого крипа.

Для spawn occurrence=0 в пределах одной generation замены. Для повторяющейся работы occurrence включает assignmentId и номер самостоятельного рейса/шага, хранимый в состоянии назначения: два последовательных transfer одного перевозчика — **две** операции, а повтор попытки одного transfer сохраняет его ключ. Следующий номер открывается после подтверждения завершения/неисполнения предыдущего либо его осторожного retirement; UNKNOWN не позволяет молча увеличить номер и повторить тот же расход. Частичный transfer сохраняет ключ и confirmedAmount до закрытия согласованного количества, следующий самостоятельный груз получает новый ключ. Для движения назначение хранит номер шага и целевую клетку; не выполненный шаг перепланируется с тем же occurrence, новый подтверждённый шаг открывает следующий. После reset счётчики восстанавливаются вместе с assignment; при утрате — сверка/UNKNOWN, не сброс на ноль. Живое поколение feeder таким образом не ограничивается одной доставкой.

Резервирования различаются:

- `SPEND`: расход энергии на тело/build/upgrade/defense;
- `MOVE`: право переместить уже учтённый груз между двумя узлами;
- `CAPACITY`: место в store/полоса spawn/назначение исполнителя.

SPEND не равен MOVE. Подтверждение внутреннего transfer снимает source/target locks и увеличивает метрику доставки, но **не добавляет энергию к новому Snapshot**, в котором она уже есть. Подтверждение spawn снимает денежное обещание и отмечает стоимость операции один раз, но не вычитает стоимость ещё раз из наблюдаемого остатка. Forecast использует подтверждённые факты и будущие уникальные платежи по stableKey; одни и те же средства не считаются одновременно cargo, pile, stock и доходом.

Состояния операции: `PREPARED → ISSUED → CONFIRMED | NO_EFFECT | UNKNOWN`. Частично подтверждённое количество хранится в поле confirmedAmount и освобождает соответствующую долю reservation; остаток не становится успехом по таймауту. Для повторения сначала проверить актуальные предпосылки и отсутствие уже исполненного spawn/доставки, затем получить новый commandId. Принятые engine-операции не отменяются изменением Memory.

| Операция | Минимально достаточное свидетельство | Что не является доказательством |
| --- | --- | --- |
| Spawn | Единственный собственный writer; заранее заданное уникальное имя/ключ, совпадающие body/home binding, реальное spawn.spawning или новый spawning/live creep | Только OK, исчезновение энергии, только старое expiryTime |
| Transfer/withdraw | Событие нормализовано в источник→получатель и однозначно сопоставлено выданному действию; подтверждён фактический amount | Общий прирост store при нескольких возможных причинах |
| Pickup/drop | Однозначная дельта участников при полном соседнем снимке и учёте decay/конкурентов либо проверенный runtime witness | Исчезновение pile без идентификации получателя |
| Build/repair/upgrade | Проверенные события/дельты в контексте body, boost, остатка работы и конкурирующих действий | BUILD.amount как универсальный расход энергии |
| Move | Наблюдаемая позиция исполнителя в следующем тике и обновлённая доступность маршрута | Принятый moveTo, стоимость PathFinder |

Идентичность события — `(roomName, effectTick, originalArrayIndex)` исходного неизменённого event log; фильтрация не перенумеровывает его. Сохраняются fingerprint исходного массива и processed cursor. Один и тот же key не обрабатывается дважды; одинаковые actor/type/amount на разных индексах не схлопываются. Matcher связывает мультимножество событий с мультимножеством команд; если однозначного соответствия нет, результат UNKNOWN, а не произвольный выбор. Потерянный интервал помечается gap, не заполняется выдуманными нулевыми событиями.

Room event log не хранит наш operationKey и доступен не за любой пропущенный интервал. При неоднозначности уменьшается доверие модели, а не подгоняется бухгалтерия. Отдельно сохраняется стоимость/результат самого проекта и качество наблюдения: потеря доказательства не доказывает ни успех, ни отсутствие расхода.

UNKNOWN не должен навсегда держать деньги, которых уже нет в мире. Его денежное обещание можно закрыть как `UNKNOWN_RETIRED` **без признания CONFIRMED**, только когда Reader видит полный текущий баланс затронутых узлов, старый intent уже не может дать отложенный эффект и доказанно отсутствуют **все возможные** живые/spawning/отложенные продолжения этой операции. При неполном binding множество кандидатов нельзя объявлять пустым: необходима сверка имени, creation envelope, body и всех затронутых исполнителей; если происхождение остаётся неясным, retirement запрещён. Для MOVE/CAPACITY дополнительно видимы оба узла и проверена доступность ёмкости после всех возможных продолжений. Текущий остаток становится новой физической базой, возможный расход до upper bound занимает лимит старой миссии при наличии восстанавливаемой записи; неизвестный доход не начисляется. Исходная запись остаётся в истории. Новая попытка — новая generation после проверки актуальной потребности, со своим бюджетом, а не replay неподтверждённого платежа. При отсутствии видимости/латентном эффекте reservation сохраняется спорным и необязательные траты этого узла закрыты. Так сохраняются ограничение риска и возможность аварийного восстановления без ложной гарантии exactly-once.

### Пропущенные окна и потерянные записи

lastClosedTick проверяется против T−1. Разрыв, missing operation при найденном новом creep, конфликт сведений или необъяснимый баланс переводит домен в UNCERTAIN_FUNDING. Проверка отсутствия CLOSE обнаруживает только часть отказов; без долговременного внешнего журнала нельзя обещать обнаружение всякой потери записи или точный прошлый missionExposure. Все гарантии дедупликации ограничены сохранившимися ключами, созданными в мире объектами и доступными наблюдениями.

В UNCERTAIN_FUNDING запрещены новые необязательные расходы и повтор старых дорогих команд по предположению. Reader строит базу из текущих реально видимых запасов; Reconciler ищет всех собственных live/spawning кандидатов, включая созданных без sidecar. Новые spawn получают короткий creation envelope в `creep.memory.strategy = {operationKey, homeRoom, ownerEpoch}` при создании; это часть памяти нового крипа, а не поле строгого Resource. Совпадающие envelope/body/владелец/уникальное имя позволяют восстановить binding. Одного хеша имени без доказуемого полного ключа недостаточно: orphan карантинируется, учитывается как существующая мощность лишь в доказанной способности и не дублируется автоматически.

Если старые расходы нельзя восстановить, метрики окна помечаются неизвестными; затронутые старые миссии закрываются/приостанавливаются без дополнительных расходов, их неизвестный остаток лимита считается исчерпанным, а не свободным. Для потерянной целиком миссии точного лимита обещать нельзя: сохраняется запись неопределённого окна. Подтверждённый критический дефицит может получить новую ограниченную восстановительную потребность только после поиска всех live/spawning кандидатов и проверки текущего бюджета; это не повтор старой команды и не доказательство отсутствия старого расхода.

Возврат к новым необязательным проектам требует полного текущего баланса, отсутствия неразрешённых кандидатов/латентных операций и 300 последовательных тиков новых согласованных наблюдений. Последнее не восстанавливает историю: прошлое окно остаётся UNKNOWN, старые миссии не получают новый лимит автоматически. Если условия недостижимы, домен остаётся ограниченным до совместимого восстановления. Это сознательная граница автономности при потере доказательств.

## 6. Состояние, версии и восстановление runtime

Авторитетное состояние хранится под отдельным `Memory.strategy`. Чужие namespaces и legacy Memory не удаляются. Представление первой схемы:

```text
strategy = {
  schemaVersion: 1, policyVersion, buildId, revision, lastClosedTick,
  control: { rooms: { [room]: {
    requestedMode, effectiveOwner, epoch, transitionPhase, transitionId,
    previousOwner, blockedReason
  }}},
  rooms: { [room]: {
    mode, maturity, stableSince, observedAt, topologyVersion,
    forecastCursor, flowWindows, decisionRing, proposalCursor
  }},
  missions: { [missionId]: Mission },
  demands: { [stableKey]: Demand },
  bindings: { [creepName]: {
    homeRoom, ownerEpoch, originEpoch, legacyOrderId, operationKey,
    demandKey, generation, assignmentId, observedLifeState
  }},
  assignments: { [assignmentId]: Assignment },
  ledger: { reservations, funds, missionExposure },
  operations: { [operationKey]: Operation },
  faults: { [domainOrComponent]: FaultStatus },
  migrations: { version, cursor, sourceRevision, status }
}
```

Каждый persisted record имеет id/key и schema-defined enum, даты и ссылки на ID. Никаких Game-объектов, Map с методами, RoomPosition-прототипов, циклов, NaN/Infinity/undefined как значений обязательных полей. Необязательное неизвестное значение — `null` вместе с quality/reason, чтобы JSON round-trip не превращал неизвестность в корректный ноль. Списки body и позиции — простые данные. Действующие объекты по id разрешаются заново каждый тик.

StateCodec валидирует записи по namespace и локализует повреждение: дефект одной миссии не делает все комнаты пустыми. StateStore применяет патчи копированием затрагиваемого домена и заменой ссылки только после validation. `revision` растёт после каждого принятого пакета; открытие state повторно в том же тике возвращает тот же session, не вторую независимую копию. Checkpoint после CRITICAL и после EXECUTE — запись полей в Memory, не принудительный durable commit на сервер. Финальная сериализация остаётся механизмом runtime.

Версии: отсутствие namespace создаёт пустую schema1 с effectiveOwner=legacy; поддерживаемая версия загружается. Миграция известной старой схемы выполняется по registered цепочке `vN→vN+1` над отдельным draft. Каждая цепочка обязана иметь совместимый reader и SafetyKernel исходной версии, чтобы откладывание/отмена не оставляли приложение без исполнителя. v1 выбирает **freeze источника**, а не непрерывное применение новых записей: после RECONCILE и до новых intents фиксируется полный source snapshot, sourceRevision и fingerprint сериализованного исходного namespace. На время переноса все writers Memory.strategy (control, ledger, reconciliation, метрики и новые bindings включительно) заморожены; курсор/draft/status живут отдельно в Memory.strategyMigration. Ни одна новая adaptive-команда не выдаётся, owner не переключается. Legacy-домены могут продолжать ограждённые старые действия, не пишущие Memory.strategy; их физический результат сверяется после переноса.

Миграция стартует только без unresolved operations, при запасе не менее 100 тиков до ближайшего critical deadline и отсутствии угроз во всех adaptive-доменах. Она имеет максимум 10 тиков и ограничение CPU на каждый блок. Новый hostile, близкий срок, изменение исходной revision/fingerprint или истечение 10 тиков отменяют draft: исходный state остаётся, совместимый reader/SafetyKernel возобновляют критическую работу, новый старт не раньше 100 тиков и только при новых безопасных предпосылках. При внешнем изменении исходной Memory не пытаться молча включить эти данные в старый draft. Reset продолжает только draft с тем же fingerprint; иначе отменяет его.

Финальный swap требует повторного сравнения sourceRevision **и** fingerprint, validation целевого draft и свежего снимка мира. После swap полный RECONCILE обрабатывает промежуток заморозки как пропущенное окно; до его завершения новые intents/смена owner запрещены. Неатрибутируемые исторические события остаются UNKNOWN. Миграция не является снимком мира и не возвращает потраченную энергию. Нет постепенной записи несовместимых полей в действующее дерево; остальные новые namespaces обновляются только после успешного swap и по явному контракту версии.

Неизвестная более новая схема или повреждённый control не преобразуются в «пустой мир». Этот namespace сохраняется; adaptive/legacy side effects для неподтверждённого владельца блокируются. Проверенный SafetyKernel может работать только при отдельно подтверждённом известном owner/control и понятной текущей способности, без чтения неизвестных структур. Если такое право нельзя установить, режим домена `SUSPENDED` и диагностическая запись через совместимый доступный канал; нужен совместимый артефакт/восстановление. Автоматическое включение старого dist2 по ошибке схемы запрещено.

Heap cache хранит `(buildId, schemaVersion, policyVersion, room, topologyVersion, inputFingerprint)`. На reset он просто пуст. Кэш результата не содержит единственную копию миссии, имени создаваемого крипа, фонда или обещанного платежа. Дорогой расчёт имеет persisted вход/cursor только если он укладывается в лимиты; иначе возобновляется с начала как UNKNOWN и не блокирует критические действия.

Ретенция v1: 30 окон потоков ×100 тиков и 100 значимых решений на комнату, как в DESIGN; максимум 256 незавершённых операций на комнату, 10 мест зарезервировано для critical. При заполнении лимита прекращается приём необязательных команд, не удаляются спорные операции ради места. Для последовательных occurrence завершённые шаги compact в монотонный closed-through watermark по assignment/action и агрегат расходов/потока; незакрытые пробелы не перескакиваются. Это позволяет не хранить тысячи полных записей движения. Завершённые разовые операции compact в агрегат/дедуп-запись по ключу; ключи живых потребностей/spawning не удаляются. После закрытия generation и отсутствия ссылок подробности хранятся 1500 тиков, затем удаляются; следующий generation имеет иной ключ. Локальные/удалённые intel записи удаляются через 30 000 тиков без наблюдений, кроме ссылок активных миссий — те остаются stale/unknown. При превышении 256 KiB сериализованного нового state закрывается приём новых необязательных миссий и запускается ограниченная compaction; чужую Memory лимит не освобождает. Неразрешённые факты не стираются ради цифры: остаётся деградация/экспорт диагностики.

## 7. Ошибки и исполнение действий

FaultBoundary находится вокруг конкретной комнаты/модели/исполнителя, а не всего приложения одним catch. Планировщик не имеет побочных эффектов; его исключение отклоняет только его новый proposal. Если нет изменения входа, повтор ошибки допускается не раньше чем через 25 тиков; три последовательные ошибки включают circuit breaker на 100 тиков. Критическое наблюдение и проверенный SafetyKernel не ждут этого cooldown. Ошибка одной роли не пропускает других крипов и записанные факты остальных комнат.

Gateway ловит обычное исключение API, сохраняет attempted action и запрещает второй вызов того же actionSlot в T. Если неизвестно, дошёл ли вызов до engine, операция UNKNOWN; нельзя попробовать другую дорогую команду тем же ресурсом. Фатальное прерывание процесса не ловится JavaScript catch, поэтому на следующем тике отсутствие CLOSE запускает полную сверку, а не объявляет rollback. Повреждённый StateStore/ledger блокирует необязательные расходы затронутого домена.

IntentArbiter заранее выбирает совместимый пакет по таблице движка; консервативный v1 допускает на creep один MOVE, одно действие из `harvest/build/repair/upgrade/attack/dismantle/heal/ranged` и одну операцию переноса, **только если** проверена их совместимость и общий начальный запас. При сомнении выбрать одно по criticality/deadline/stableKey. На структуру — одно действие; на имя spawn — одна операция; safe mode — одно решение координатора. Этот набор намеренно может использовать меньше разрешённых комбинаций, но не полагается на случайный порядок вызовов. Планировщики и собственный боевой rollout получают ту же capability-таблицу, что Arbiter: нельзя прогнозировать одновременные собственные действия, которые исполнитель затем запретит. Полную таблицу совместимости расширять отдельными проверенными сценариями. Селектор отклоняет второй intent того же слота, а не молча перезаписывает первый.

SafetyKernel имеет короткий конечный набор действий по текущим проверенным фактам: снабжение/защита уже действующими исполнителями, минимальное обслуживание downgrade, отход из опасной клетки, восстановительный spawn только при известном владельце, сверенных живых/spawning связях и доступном пакете. Он пользуется теми же Gateway/slots и доступными финансовыми ограничениями; не создаёт параллельную стратегию. При неподтверждённом ledger допускаются только заранее проверенные локальные защитные действия с наблюдаемым запасом и ограниченным расходом; новые spawn/миссии ждут сверки. Остаточный риск невозможного восстановления из неизвестного состояния фиксируется, не скрывается обещанием безопасности.

## 8. Сквозной сценарий: погиб перевозчик спавна

Предпосылки примера: комната RCL2, owner adaptive epoch=7, один свободный spawn с energyAvailable=300, доступный источник и pile, действующий добытчик, нет угрозы. Feeder `oldMule` исчез после предыдущего наблюдения; других подходящих/spawning перевозчиков нет. Шаблон `2 CARRY + MOVE` стоит 150, capacity=100, базовое время spawn=9 тиков. Дальность и циклы сначала верхние расчётные, затем измеренные. Времена рождения/прихода ниже подтверждаются снимками, а не предполагаются из календаря.

```mermaid
sequenceDiagram
    participant R as Reader / Reconciler
    participant G as Governor / Scheduler
    participant L as Ledger / StateStore
    participant I as Gateway
    participant E as Screeps engine
    R->>G: T: missing oldMule, live/spawning coverage=0
    G->>L: demand feed-spawn, generation=2, body150
    L-->>G: reserve SPEND150 + spawnSlot, revision accepted
    G->>I: operationKey room/epoch7/feed-spawn/gen2/spawn/0
    I->>E: spawnCreep(body, stableName)
    E-->>I: OK (call accepted)
    I->>L: ISSUED; effect not confirmed
    E-->>R: T+1: spawning/name/body observed
    R->>L: CONFIRMED start, binding=SPAWNING, no duplicate order
    E-->>R: T+k: creep spawning=false
    R->>G: BORN, travel still needed
    G->>I: move / pickup / transfer tasks with reservations
    E-->>R: transfer event + next snapshot
    R->>L: confirmed amount, MOVE locks released, delivery metric
    R->>G: first delivery verified; feeder capability restored
```

Подробности ответственности:

1. OBSERVE видит отсутствие старого крипа в Game.creeps, RECONCILE проверяет его home binding, исходный последний tick и реальные spawn. Пропуск видимости целевой комнаты не подменяет смерть; для собственного крипа используется доступный глобальный список с capability target runtime.
2. Потребность имеет stableKey `home/feeding/spawnId`; гибель исполнителя прекращает будущие назначения, а транспортные обещания освобождает только в доказанно неисполненной части. Выполненный в тик смерти transfer всё ещё может требовать подтверждения; неизвестная часть остаётся спорной до сверки, даже если assignment уже закрыт. Потерянный cargo не переносится обратно в доступный баланс источника. Старое generation закрывается после сверки, новое =2. Если сменщик уже рождается, новый spawn не нужен.
3. RECOVER действует сразу по событию, не ждёт 25-тикового governor. SpawnScheduler сравнивает живую альтернативу и допустимые тела, проверяет очередь/энергию. Здесь принят 150; reserved150 не означает, что остальные150 свободны для улучшателя без проверки других обязательств.
4. Gateway повторно проверяет epoch, spawn.spawning, имя и сумму доступных spawn/extensions; creation envelope и роль передаются в memory нового крипа. Подготовленный key связывается с именем в Memory.creeps нового крипа и sidecar, не добавляется к строгому legacy Resource. При OK — ISSUED, не active.
5. На T+1 наблюдаемый spawn/name/body подтверждает начало при единственном writer. Cost150 отмечается один раз. Нет EVENT_SPAWN; общий store может дополнительно измениться из-за генерации/доставки, поэтому разность store не заменяет эту сверку. Если домашний binding потерян, сначала восстановить его по creation envelope, owner и body; невозможность доказать соответствие оставляет orphan/UNKNOWN. Появившийся spawning creep ещё не считается 100 единицами работающей перевозки.
6. После реального рождения AssignmentScheduler выдаёт маршрут. Pickup требует количества и доступности pile; до подтверждения груз не считается доставленным. Единичная UNKNOWN загрузка не превращается в READY-контур. При однозначном transfer в spawn событие source→target подтверждает фактическую доставку. Feeder-статус HEALTHY требует первой подтверждённой доставки; stableSince начинает новый интервал, а не наследует 1500 «стабильных» тиков до аварии.

| Вариант отказа | Результат приложения |
| --- | --- |
| ERR_BUSY / недостаток энергии | NO_EFFECT только если контракт API это подтверждает; перепланировать срок/тело, не терять Demand |
| ERR_NAME_EXISTS | Сверить существующий key/body/home; совпадение — восстановить binding, конфликт — карантин имени, без автоматического дубликата |
| Reset после API до записи receipt | Сверить spawn/name и реальные creeps до повторной выдачи; missing journal не доказывает отсутствие действия |
| Новый крип уже погиб до восстановления наблюдения | Исторический расход может остаться UNKNOWN; новый актуальный дефицит получает новую generation после сверки и свой бюджет |
| Исчез pile / target заполнился | Освободить только доказанно неисполненную часть назначения, пересчитать цель; не считать доставку выполненной |
| Смена owner epoch в пути | Старый executor не действует; binding перенесён координатором либо удерживается на ограждённом совместимом исполнителе |
| Пропущено событие доставки | UNKNOWN, качество потока снижено, новые назначения по текущим реальным запасам; не выдумывать подтверждённый доход |

Эта трасса — спецификация ожидаемых переходов, не полученная игровая трасса. Реальный тест должен сохранить соседние snapshots/intents/event logs и привязать все даты к откалиброванной фазе engine.

## 9. Проверки по слоям и границы этапа A

| Слой | Проверяется без движка | Требует isolated engine/runtime |
| --- | --- | --- |
| Domain/модели | Дефицит резерва без дубликатов, фонды, сроки, tie-break, unknown вместо нуля | Калибровка стоимости, фаз и реальных циклов |
| Snapshot/Replay | Сортировка, DTO serialization, одинаковый input → одинаковый plan/reasons | Видимость, event direction, deaths/spawning и полнота данных |
| StateStore | Version/migration/revision, reset из JSON, bounded history, локальный карантин | Exception/timeout/serialization при реальном драйвере |
| Ledger/Gateway | Нет двойного резервирования, slot conflicts, UNKNOWN-retirement | Accepted intent vs реальный effect, конкуренты и неоднозначная дельта |
| Legacy/shadow | В shadow нет capability Gateway и патчей legacy | Отсутствие эффектов на initialize, actual deploy resolver и mixed owners |
| Lifecycle | Пакет переходит Demand→Assignment→Operation без дублей | Трасса перевозчика, смерть, reset и повторное переключение |

ReplayFixture содержит policy/build/schema, seed при наличии, Snapshot DTO, выбранные поля StateView, нормализованные предыдущие события и ожидаемые reason codes. Никаких credentials и дампа всей чужой Memory. Данные сохраняются по явной команде в локальный тестовый артефакт; публичные отчёты не копируют приватный мир. Предлагаемое размещение тестов — `tests/bot/unit`, `tests/bot/replay`, e2e расширяется через существующую одноразовую обвязку. Локальные тесты чистых моделей не подменяют результат действий движка.

Этап A реализует composition root/сборку, Reader/DTO, StateStore schema1, наблюдатель эффектов, финансовый календарь и shadow proposals с журналом. В legacy/shadow фактический owner остаётся legacy; новая система не создаёт новых крипов, не переключает комнату adaptive и не запускает боевой rollout. Если необходимого witness нет, отчёт выводит UNKNOWN и объясняет, какие данные нужны. Это завершённый полезный результат, даже если часть дохода пока нельзя строго атрибутировать.

Приёмка этапа A: экспортируемый replay воспроизводит прогноз и причины; таблица энергии не считает transfer новым доходом; события пропускаются/дублируются в тесте без ложного успеха; reset сохраняет идентичности, но не фиктивные Game-ссылки; ни один shadow-run не выдаёт intents и не мутирует legacy state; собранный main загружается и не создаёт adaptive заказов при require. Допуск adaptive, migration cutover и восстановления из неизвестных схем проверяются отдельно перед этапом B. Полный боевой прогноз и remote остаются этапами D/E стратегического дизайна.

Первые задачи реализации следует делить по этим контрактам: scaffold/build+runtime ports; snapshot/replay; codec/store; evidence reconciliation; финансовые модели; shadow integration. Одинаковый интерфейс DTO позволяет выполнять независимые части параллельно, но только после фиксации версии этого контракта. Настоящая задача завершает архитектуру, а не создаёт разрешение на развёртывание.
