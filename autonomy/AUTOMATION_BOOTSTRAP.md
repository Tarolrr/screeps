# Scheduler bootstrap

No schedule is configured or active through this kit. GitHub Issues is the sole active queue; the migrated `state/tasks.json` is a read-only archive and not a fallback. Creating or enabling one requires a separate explicit owner instruction. After authorization, the owner must select and configure the actual project scheduler, confirm its identity and delivery of `AUTOMATION_PROMPT.md`, and arrange `SCREEPS_AUTOMATION_ORIGIN=scheduled` and `SCREEPS_AUTOMATION_ID=<project automation ID>` for each invocation. Do not reuse another project's identity or credentials.

The optional Happier self-pause adapter reads `~/.config/screeps-strategy/automation.json` outside the checkout. It defaults to disabled when missing or invalid. Only after explicit activation, create a private file with `enabled: true`, `automation_id`, `server_id`, and `server_url`; the latter must be a local HTTP(S) server URL. The ID must be alphanumeric; the server ID permits letters, digits, dot, underscore and hyphen. The helper reads credentials from that configured server's Happier access file without printing them, refuses redirects, sends a single pause POST and checks GET readback. Configure the scheduler's metadata to match the same project ID. A mismatched or missing identity fails closed. Do not place secrets in the repository.

Verify configuration without network using `python3 autonomy/automation_pause.py --check`. This checks local configuration and credentials, not scheduling or pause behavior. Before enabling, review PROCESS and RECOVERY and test only against an isolated mock service.

Scheduled finalization replaces the retired `coordination.py release` hook (ADR 0002). A scheduled run calls `automation_pause.py --finalize --owner OWNER [--task issue-N]` before `autonomyctl.py finish`. Without both metadata values it is a manual run and does nothing; mismatched metadata fails closed. It pauses only when the GitHub queue has no ready, in-progress or review work and the v2 registry under `<git-common-dir>/autonomy-coordination-v2/` holds no task claim other than the caller's own live claim with no recorded runs. The registry flock is held only to check and record the attempt, never during the queue read or HTTP. A pending receipt (`automation-pause-result.json`, keyed by automation ID, owner, task and the claim's acquisition time) is written before the POST, so a crash or lost response is not retried. The helper never claims, recovers or finishes tasks; a failure is reported in its JSON output and the run still finishes its claim. Review the error and do not retry an uncertain pause blindly. Both checks have a race window: the queue is read outside any lock, and the registry check is not held during HTTP, so an issue that becomes ready or a session that claims a task right after the checks is not seen. Such work is not stopped by the pause; the pause only prevents further scheduled runs until the owner resumes them. Without `--task`, a successful receipt is not replayed (the owner may have resumed the schedule since); pending or failed receipts still block a blind retry.
