# Process

A top-level session converts each actionable request into a GitHub issue in `Tarolrr/screeps` with acceptance criteria, priority and dependencies before delegation. Coordinate non-overlapping delegate scopes inside a task. Prefer native subagents and, where available, the lightweight `gpt-6.1-terra` model; use Happier-managed workers only on explicit user request. Delegation depth is one on every route; delegates are leaves and never start agents, sessions or runs. System, developer and user instructions govern whether delegation is allowed. A read-only reviewer independently assesses the result and evidence; report when that is unavailable. Only top-level sessions edit issues, labels and comments and make the acceptance decision. See GITHUB_ISSUES for the status and dependency model; the local task file is a read-only migration archive and never a fallback. Users' instructions and already granted scope continue to apply; no blanket publication, external messaging, server mutation, spending, or scheduler activation is inferred from this kit.

## Task lifecycle and integration

1. Claim the issue's task (`autonomyctl.py claim --task issue-N`) and set `status:in-progress`. Run `git fetch`, then create its worktree (`workspace-create`, base `origin/master`); all writes for the task happen there. Several tasks run in parallel in separate worktrees.
2. Delegate bounded scopes, heartbeat with delegate references, claim named resources only while mutating them ([RECOVERY](RECOVERY.md)).
3. When evidence and the review verdict are recorded, commit the task's scope on the task branch in its worktree as an issue-referencing commit. Intermediate commits are optional. HANDOFF.md updates are made on the task branch as a short dated entry at the top; conflicts with other tasks' entries are resolved at integration.
4. Integrate as a short serialized step from the task worktree (`master` stays checked out only in the shared main checkout; do not switch it): `resource-claim --resource integration:master`, `git fetch`, `git rebase origin/master`, re-run the checks affected by the combined change, `git push origin HEAD:master`, then `resource-release`. A PR is an alternative. Fast-forward the main checkout (`git -C MAIN merge --ff-only origin/master`) only if it is clean; otherwise leave it and note it. Conflicts are resolved on the task branch; if that turns into task work, release `integration:master` first and retry later. Files touched by several tasks are reconciled here and noted in the commit message.
5. Close the issue, clear runs, `finish --outcome done --commit SHA`. When finishing with `blocked` or `abandoned`, first set the issue to `status:blocked` (with reason) or back to `status:ready`; never leave `status:in-progress` without a claim. Remove the worktree only after integration or explicit abandonment.

Run artifacts under `*/.runs/` are local disposable evidence and are not committed; verdicts and run ids live in docs and issue comments.

## Run outcomes

A run may produce useful work, be idle (no ready unclaimed work and no new facts), busy (the task it would take is claimed by someone else — pick another ready task, or stop if none), or blocked (a necessary action or information is unavailable). Claims of other tasks are never a reason to stop. Idle starts with read-only inspection and makes no tracked changes, commits, pushes, builds or redundant verification delegates. Busy never takes over, recovers or releases another session's claim. Do not invent new facts to justify a cycle.

For noninteractive scheduled runs, do not wait for answers. If required information is missing, record `blocked` with `blocked_reason: needs_clarification`, `missing_information`, and the next action for a manual top-level session. Dependencies of blocked tasks are not ready. Complete and stop delegates, clear runs, and finish your claim (`--outcome blocked` if applicable). Report errors without exposing credentials.

## Scheduled finalization

If a run is known to be scheduled, that origin persists throughout the run. Before `finish`, a scheduled run calls `python3 autonomy/automation_pause.py --finalize --owner OWNER [--task issue-N]` (omit `--task` if the run claimed nothing). It reads `SCREEPS_AUTOMATION_ORIGIN`/`SCREEPS_AUTOMATION_ID`; without both values it is a manual run and does nothing. It pauses the configured project automation only when the GitHub queue has no ready, in-progress or review work AND the v2 registry holds no task claim other than the caller's own live claim with no recorded runs (any other claim, even expired, means work may be running). If origin is known from delivery but metadata is missing, explicitly invoke `automation_pause.py --owner OWNER [--task issue-N] --automation-id ID`. Never infer a manual run from missing metadata. Queue errors are not idle. A durable receipt prevents a repeated POST for the same task claim; without `--task` a pending or failed attempt still blocks a retry, but an earlier success does not (see AUTOMATION_BOOTSTRAP). Do not retry an uncertain pause blindly. Pause failure is reported and never blocks `finish`. No automatic resume: owner activation is explicit. A manual run never pauses the schedule merely because the queue is empty.
